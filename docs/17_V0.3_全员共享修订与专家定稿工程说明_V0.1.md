> 状态：冻结实施基线
>
> 日期：2026-08-13
>
> 适用范围：广告视频专业域 V0.3-PILOT
>
> 上游基线：`docs/13`、`docs/14`、`docs/15`；发生冲突时以本文为准
> 代码基线：`origin/main@40d503f`

## 一、目标与成功画面

V0.3 从“每位用户针对同一作品各自拥有一份作业”改为“每个作品只有一条公司共享协作主线”。V0.2 映射结果成为公共 V0.3 的初始基线，所有 ACTIVE 登录成员默认读取同一份非空共享内容，并可在同一工作稿上批注和直接修订。

必须同时成立：

1. 一作品一条 V0.3 共享主线，同一时刻只允许一个活动协作轮；
2. ACTIVE 成员均可查看、批注和直接修订稳定内容单元；
3. 每次修订留下不可变的操作者、时间、目标、修订前值、修订后值、原因和基础修订号；
4. 并发写入使用工作稿修订号进行乐观锁校验，冲突返回 409，客户端保留本地内容；
5. 原作者仅作来源与署名展示，不构成查看、批注或修订权限边界；
6. 仅 `app_admins` 中的专家可定稿、恢复历史定稿版或改变当前展示标准；普通成员对应 API 返回 403，页面不展示入口；
7. 定稿生成永久不可变的批准版本；后续修订进入以该批准版本为基线的新协作轮；
8. 恢复旧批准版只创建新的恢复轮，不覆盖当前或历史正文；
9. 即使当前工作稿被软删除或内容被清空，初始基线和全部批准版本仍能独立查看并由专家恢复；
10. V0.2 始终作为历史只读数据，不就地重解释或覆盖。

| 新增批注、回复批注 | 是 | 是 | 是 | 否 |
| 直接修订共享工作稿 | 是 | 是 | 是 | 否 |

## 三、状态机

### 3.1 共享主线

- `ACTIVE`：作品的公共 V0.3 主线可正常协作；
- `ARCHIVED`：只允许系统迁移或未来显式归档使用，本轮不提供普通入口。

一作品、一个体系版本最多一条共享主线。

### 3.2 协作轮

- `ACTIVE`：唯一可写的共享工作轮；
- `FINALIZED`：该轮已由专家定稿，正文冻结；
- `SUPERSEDED`：因专家从另一历史版本恢复而结束；
- `SOFT_DELETED`：当前可变工作轮被软删除；基线和批准版不受影响。

活动轮的来源为：

- `INITIAL_BASELINE`：从 V0.2 映射稿或既有 V0.3 建立；
- `APPROVED_RELEASE`：上一批准版定稿后开启；
- `RESTORED_RELEASE`：专家从历史批准版恢复；
- `EMPTY_INITIAL`：作品尚无任何可映射内容时显式创建。本轮禁止因访问页面自动生成。

### 3.3 候选与定稿

- 工作稿可持续保存，状态为 `DRAFT`；
- 任一成员可把当前修订号标记为 `READY_FOR_FINALIZATION`，由不可变候选快照承载；
- 候选不锁死共享主线，后续直接修订会使旧候选变为 `STALE`；
- 专家只能批准当前共享修订号对应的有效候选，或在界面中明确选择并重新确认的候选；
- 批准后生成不可变 release，结束当前轮并从该 release 自动开启下一轮。

## 四、页面入口与术语

作品页固定分为：

1. **当前公共 V0.3**：默认展开；显示来源署名、活动协作轮、工作稿修订号、最后修订者和更新时间；
2. **共享协作记录**：按时间显示批注与直接修订，修订记录展示 before/after 和操作者；
3. **历史定稿版**：显示当前活动批准版与全部历史批准版；专家可从任一历史批准版创建恢复轮；
4. **V0.2 历史只读**：降权展示，原数据和版本保持不变。

编辑入口统一命名为“编辑公共 V0.3”或“进入共享修订”。禁止再使用“我的 V0.3”“我的个人作业”“开始一份个人分析”等会暗示个人分叉的文案。

读取作品页、公共 V0.3 或历史版本均为只读动作，不得隐式创建 annotation、主线、协作轮或空白稿。共享数据结构已经部署、但单个作品尚未完成受控接入时，读取层必须按照与 PREVIEW 相同的确定性顺序回退展示既有非空 V0.3，并标记“待接入共享主线、只读”；只有确实不存在任何既有 V0.3 时才显示明确空状态。

### 4.1 安全发布顺序与兼容要求

1. 共享代码部署必须先向后兼容尚未 APPLY 的既有 V0.3，不能把 schema 存在等同于业务接入完成；
2. 标准顺序仍是代码部署 → PREVIEW → 核对 → 分批/整批 APPLY → 复核，但任一步暂停都不得导致既有内容不可见；
3. PREVIEW 数量、作者、状态或版本与冻结范围不一致时必须暂停 APPLY，不得暂停只读回退；
4. 回退状态只读，不创建个人空白稿、不写协作事件；管理员可从明确入口进入受控接入工具；
5. APPLY 完成后，同一 URL 自动切换到共享主线，不需要复制或重写正文。

## 五、数据对象与关系

### 5.1 `v03_collaboration_streams`

一作品一条共享主线：

- `video_id`、`taxonomy_version` 唯一；
- `canonical_annotation_id` 指向当前共享可变正文；
- `initial_baseline_id` 指向不可变初始基线；
- `active_round_id` 指向唯一活动协作轮；
- `active_release_id` 指向当前展示的批准版（可空）；
- 保存建立来源、状态和审计时间。

该对象只建立公共寻址，不迁移或删除旧 annotation。

### 5.2 `v03_collaboration_sources`

记录共享主线与既有 annotation 的关系：`CANONICAL`、`LEGACY_CONTRIBUTOR`、`MAPPED_SOURCE`。它允许保留旧个人线、旧快照和批准记录，同时明确当前公共主线使用哪一条 annotation。

### 5.3 `v03_collaboration_baselines`

不可变初始基线，保存完整 canonical payload、内容哈希、来源 annotation / snapshot / 映射 operation、来源作者和建立时间。正文不依赖当前 mutable children，因此当前工作稿被清空或软删除后仍可读取和恢复。

### 5.4 `v03_collaboration_rounds`

记录活动轮次、基础类型、基础 baseline/release/snapshot、开始时工作稿修订号、状态、创建/结束操作者与时间。使用部分唯一索引保证每条主线最多一个 `ACTIVE` 轮。

### 5.5 `v03_collaboration_revision_events`

每次共享保存产生一个 change set，内含一个或多个稳定目标事件：

- `round_id`、`annotation_id`、`base_revision`、`applied_revision`；
- `target_key`、`target_label`、`value_type`；
- `before_value_json`、`after_value_json`；
- `reason`、`actor_email/name`、`created_at`；
- `change_set_id` 将同一次保存的跨字段改动组合起来。

事件只追加，不更新、不物理删除。稳定目标采用现有 `analysis-targets` 的类型化 key；数组增删、镜头重排和桥段结构变化使用完整结构 JSON 记录，不伪装成字符串选区。

### 5.6 现有对象的兼容关系

- `annotations`、`shots`、`shot_groups`、`field_answers`、`annotation_creative_structures`：继续承载当前共享可变正文；
- `annotation_snapshots`：继续承载候选、历史提交和批准快照；
- `analysis_comments`：继续保存批注，但 V0.3 允许绑定共享轮与对应基础工作稿修订；旧 snapshot/review-round 绑定保留；
- `analysis_review_rounds`：继续承载候选定稿过程，不再表达“作者与终审者的专属权限”；
- `approved_analysis_releases`：继续作为批准版，增加共享主线/协作轮血缘；payload 和 content hash 永久不可变；
- `audit_logs`：记录主线建立、共享保存、候选提交、专家定稿、恢复和软删除。

## 六、不可变量

1. 同一作品的 V0.3 只有一个共享主线、一个 canonical annotation 和最多一个活动协作轮；
2. GET 请求不得创建任何业务数据；
3. `v03_collaboration_baselines`、`annotation_snapshots`、`approved_analysis_releases`、协作修订事件只追加；
4. 保存共享稿必须在同一事务内锁定 canonical annotation、校验 `baseRevision`、更新正文、写 revision events 和审计；任一步失败全部回滚；
5. 批准必须在事务内校验专家身份、候选快照、当前协作轮、当前修订号和整案结构；
6. 批准后旧 release 只改变展示状态，不改变 payload/hash；新一轮从批准 payload 复制到可变正文；
7. 恢复历史版只创建新轮并复制 payload；不删除中间轮、修订、批注、候选或批准记录；
8. 软删除只作用于当前可变轮/正文展示状态，不级联 baseline、snapshot、release 或 V0.2；
9. V0.2 的物理字段、快照和版本号不因本改造改变；
10. 所有写入测试只使用 `TEST_ONLY` 数据并按 run id 精确清理。

## 七、现有数据迁移方案

### 7.1 代码与结构迁移

数据库结构采用增量迁移，但不在构建、普通部署或启动时自动执行。上线后由管理员在受控页面先执行显式 `INSTALL_SCHEMA`：只做 `CREATE TABLE IF NOT EXISTS`、`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`、索引和 RLS，随后校验结构就绪。该步骤不创建业务主线、不回填正文；结构未就绪时业务 `PREVIEW/APPLY` 不可用。

### 7.2 生产业务回填

使用管理员限定、same-origin、带确认口令、操作账本防重放的受控页面/API：

1. `PREVIEW`：只读枚举每个作品的 V0.3 annotation、映射来源、快照、批准版和活动 release；按确定性规则选择 canonical annotation；输出 18 份映射稿、4 份既有 V0.3 及异常项摘要；
2. 选择规则：有活动 release 时优先该 release 所属 annotation；否则优先已有公开/提交历史的 V0.3；否则使用批量映射产生的 V0.3 draft；不得按访问者身份选择；
3. `APPLY`：逐作品事务建立 stream、source、baseline 和 active round；baseline 从 canonical annotation 当前完整工作包生成；不改正文、不搬移旧快照、不重写 release；
4. 写后核对：正文哈希、V0.2 摘要、快照/批注/修订/审核/批准数量和所有非目标数据摘要必须与写前一致；异常回滚；
5. 已完成 operation key 幂等返回，不再次创建基线或覆盖后续协作；
6. 全部回填成功后入口永久只读锁定。

如线上 PREVIEW 的数量、canonical 选择、活动 release 或作者来源与冻结范围不一致，停止 APPLY 并回报项目负责人。

## 八、API 行为

- `GET /api/videos/:id/annotation?taxonomy=V0.3-PILOT`：只读取共享主线；不存在时返回明确空状态，不创建个人稿；
- `PUT /api/videos/:id/annotation?taxonomy=V0.3-PILOT`：所有 ACTIVE 成员可保存共享正文；必须提交 base revision；成功写 change set，冲突 409；
- `POST .../submit`：把当前修订号生成候选快照并标记待专家定稿；不再按作者加载；
- V0.3 批注：所有 ACTIVE 成员可创建、回复；状态处理按协作身份记录，不再限制作者/终审者才能发起；
- 批准 API：仅专家；普通成员 403；批准后冻结 release 并开启下一轮；
- 恢复 API：仅专家；显式指定历史 release id，事务创建恢复轮并更新共享可变正文；
- 历史/baseline GET：所有 ACTIVE 成员可读；无写副作用。

## 九、交互约束

1. 公共编辑页显示“当前公共 V0.3”“共享修订轮 N”“工作稿 rev N”“最后修订者”；
2. 保存成功提示变更已进入公共工作稿；冲突面板必须保留本页文字，提供加载最新版或基于最新版重试；
3. 内容单元维持现有原位“批注·修订”入口；普通成员的修订直接应用到共享稿并立即显示在历史中；
4. 专家定稿按钮只在候选与权限均满足时显示；普通成员不渲染按钮；
5. 定稿后页面立即显示新批准版和自动开启的新协作轮；
6. 历史批准版显示“只读永久版本”，专家另见“从此版本创建恢复轮”；
7. V0.2 入口固定标注“历史只读”。

## 十、验收清单

### A. 共享读取

- 原作者、另一普通成员、专家打开同一作品，返回相同 stream id、annotation id、round id、revision 和非空 payload；
- 连续 GET 前后业务数据指纹不变；访问他人作品不新增 annotation。

### B. 全员批注与直接修订

- 两名普通成员都可对同一内容单元批注；
- 两名普通成员都可直接修订，历史显示各自身份、before/after、原因和 base/applied revision；
- 使用旧 revision 保存返回 409；客户端本地内容仍在。

### C. 专家定稿

- 普通成员看不到定稿入口，直接调用返回 403；
- 专家可把当前有效候选定稿，生成 immutable release、批准快照和审计记录。

### D. 定稿后续修订

- 定稿结束旧轮并开启基于该 release 的新轮；
- 普通成员后续修订只更新新轮共享工作稿；旧 release payload/hash 逐字段逐镜不变。

### E. 恢复与抗删除

- 当前工作稿软删除或清空后，初始 baseline 和全部 release 仍可读取；
- 专家从任意历史 release 创建恢复轮；旧轮、旧批准版和中间版本全部保留。

### F. 生产兼容

- PREVIEW 精确识别 18 份映射稿和 4 份既有 V0.3；
- APPLY 仅新增共享寻址、baseline、round、source 和审计记录；
- 《欢迎回家》及其余既有 V0.3 正文、V0.2、快照、批注、修订、审核和批准数量/哈希不变。

### G. 页面语义

- 页面不再出现“我的 V0.3/我的个人作业”；
- 清楚区分当前公共 V0.3、共享轮、历史定稿和 V0.2；
- 桌面与窄屏均能完成查看、批注、修订、冲突处理、普通成员权限核验和专家定稿/恢复入口核验。

### H. 工程与发布

- `npm test`、`npm run lint`、`npm run build` 全通过；
- 写入测试仅使用 `TEST_ONLY` 夹具并精确清理，业务指纹前后一致；
- 提交前检查 diff 和暂存清单，仅提交本任务文件；
- 推送 `main` 后核对 Vercel 部署 SHA，不把 GitHub 推送当作已部署；
- 线上先只读验收，再按受控 PREVIEW→APPLY→复核→锁定入口执行业务回填。

## 十一、明确不做

- 不改变广告专业域现有字段定义和词表含义；
- 不对现有标注内容做自动润色、主观纠错或 AI 预填；
- 不把旧个人 annotation 物理合并、删除或改写；
- 不在访问页面、构建、部署或服务启动时自动创建业务主线；
- 不恢复、删除或覆盖 R5、V14 等任何真实历史记录；
- 不为未来其他专业域提前设计具体字段。
