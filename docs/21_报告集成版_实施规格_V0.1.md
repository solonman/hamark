## 一、冻结的产品规则

### 对应关系表

| 视频侧概念 | 报告侧对应 | 备注 |
|---|---|---|
| 时间线（一串镜头的播放顺序） | 页序 | 页是**固定原子**：转换流水线生成后数量、编号不再变化，工作台只能划分页的归属，不能增删页（同 `docs/19` §2.1）。 |
| 桥段（`shotGroup`） | 模块（`ReportModule`） | 直属页集合必须连续（`isContiguous`）。 |
| 镜头（`shot`，含子镜头？无——镜头不嵌套） | 讲述单元（`ReportUnit`，**可嵌套**：`pid` 指向父单元） | 报告的嵌套层级比视频深——单元可以有子单元、孙单元；视频的桥段/镜头是两层，报告是"模块 → 单元 → 子单元 → …"不定层。 |
| 桥段/镜头的标注字段（`bridgeName`、`primaryCreativeRole`…） | 模块/单元的标注字段（`name`、`rel`、`role`、`task`、`psy`、`concl`…） | 一一对应为 FIELD 记录，见 3.1。 |
| 镜头里的旁白／字幕等条目（有 id 的子对象，随镜头增删改） | 页内的内容组块 `ReportBlock`（有 id，随页增删改） | **不对应到镜头，对应到页**——组块属于某一页，不属于模块/单元；模块/单元只通过"拥有哪些页"间接拥有组块。 |
| （无对应——视频没有"桥段/镜头拥有哪些时间线区间"这种独立可变字段，区间由镜头顺序隐式决定） | 模块/单元「拥有哪些页」这件事本身，会被拖拽改变 | 报告独有的第三类结构记录：**SPAN**（页范围变更），见 3.1/3.7。 |
| `script.structure` 整体替换（valueType `STRUCTURE`） | 无——报告没有"客户端算好的变更集"，PUT 提交整份 `ReportAnnotation` payload | 汇入记录改由**服务端**用 `diffReportAnnotation(before, after)` 纯函数比较前后两份完整 payload 算出来，见 3.1 前言。 |
| `collaboration_revision_events`（细到每一次编辑的事件流水） | 无——`report_versions` 每版只存"当前 payload + revision + updated_at + 创建时快照的 `base_payload_json`"，没有版内编辑历史 | 直接影响集成版的**创建与回填**算法，见 3.3；这是报告侧与视频侧最大的架构差异，已在 3.3 里给出应对方案与已知局限。 |

以下"一、二、三、四、五、六"的每一条，先写规则本身（多数与视频侧逐字一致，只是把"桥段/镜头"换成"模块/单元/页/组块"），再写报告特有的部分。

### A. 评论跨版本展示

**已经生效，本文不新增规则**——`lib/case-review.ts`/`lib/report-review-server.ts`/`V19ReviewComment.tsx` 已经是"按条目汇总所有版本评论、标本版、只有老孙能写"的通用实现（同视频侧规格一之 A 第 1–5 条）。本文只在四、4.4 里补一件事：集成版的 id 也要能作为评论的合法锚点。

### B. 集成版（同视频侧规格一之 B，逐条对应）

1. **定义**（同 §6）：每份报告有且只有一个「集成版」，版本菜单置顶显示。它不属于任何人，内容按处取最新：任一普通版本改了哪一处，集成版的那一处就换成谁的，**后改覆盖先改**。插入/删除模块、单元、组块，以及模块/单元的页范围变化，同样汇入。
2. **两态**（同 §7）：`OPEN`（进行中）自动汇入；`DONE`（已定稿）时其他版本的修改不进集成版，只记为"未纳入"。只有老孙能「定稿」「取消定稿」。
3. **取消定稿后**（同 §8）：定稿期间产生的"未纳入"修改不自动补进，由老孙在溯源视图里逐条「采纳」或横幅上「全部采纳」。采纳按产生顺序落到集成版上。
4. **只有老孙能直接编辑集成版**（同 §9）：其他人在集成版页面碰任何输入都是只读态（报告侧的差异见五、16——报告的字段大多是"点击态编辑"的原生禁用控件，不是视频那种"点击手势 + 拦截"模型，所以不需要 `onBeforeEdit` 拦截 + toast，改用锁定态样式 + hover 提示，效果等价，交互机制不同，已在五详细展开）。老孙直接改的记为"直接修改"，进入溯源链；进行态下若之后有普通版本改同一处，照样被覆盖。老孙自己的普通版本照旧存在。
5. **两种视图**（同 §10）：`默认` 只显示每处当前采用的内容，hover 可见来自哪一版；`溯源` 在每处内容下按更新顺序列出该处所有版本的写法，标 `原稿`／`已被覆盖`／`当前采用`／`未纳入`，未纳入项带「采纳这一版」按钮（仅老孙）。**实现时请直接采用视频侧 `lib/v19-final-trace.ts` 上线后追加的简化规则**（相邻重复行合并、"当前采用"永远单独一行渲染、旧写法折叠成摘要行、未纳入完整展开）——这些规则比 `docs/20` 原文更精炼，是根据线上走查反馈追加的，报告侧没有理由退回到更笨的版本，直接照搬即可（见"报告侧新增 `lib/report-final-trace.ts`"，四、5.18）。
6. **进入页面默认展示集成版**（同 §11）：报告已有真实版本（`report_versions` 至少一行）时，`GET /api/reports/[id]/annotation` 不带 `?version=` 默认返回集成版；显式 `?version=` 指定时按指定；报告还没有任何真实版本时保持原行为（`resolveReportDefaultVersion` 挑出的虚拟 v1）。
7. **顶栏**（同 §12）：版本条在集成版视角显示 `集成版` + 状态胶囊（进行中／已定稿）；报告本来就没有"比较基版"功能（`docs/19` §6.2 已经去掉这段，`ReportVersionBar.tsx` 顶部注释也写明"报告用不上逐处差异"），所以这条对报告侧是自动满足，不用额外隐藏什么。

### C. 报告特有：SPAN（页范围结构记录）

视频没有这类记录，因为镜头/桥段的"区间"由数组顺序隐式决定，从不单独可变。报告的页是独立分配的（`ReportPage.mid`/`.uid`），拖页改边界、把页退回未归入，都是"某个模块/单元当前直属哪些页"这件事本身发生了变化，必须单独建模，见 3.1/3.2/3.7。

### D. 溯源视图在拆解区（第三部分）的呈现

- **模块/单元收纳框**：标题栏下一行新增来源提示"这段划分来自 vN 谁 时间"（对应它当前直属页集合最后一次被 SPAN 记录确定的来源）；被覆盖的旧划法（页范围）折叠列在下面，格式同字段的"旧写法摘要行"（v19-final-trace 的简化规则 3：一行摘要、可展开）。
- **字段脚注**：每个可编辑字段正下方"当前采用 · vN 谁 时间"，与视频侧完全一致的样式与交互，见四、5.18/5.19。
- **横幅未纳入的结构改动**：与视频一样列在横幅下方，一句话 + 采纳按钮，但报告要覆盖五种结构动词（新增/删除模块、新增/删除单元、新增/删除组块、页范围变更），见四、5.18。

## 二、数据

新增两张表，附加式：新增 `db/report-final-schema.ts`（导出 `REPORT_FINAL_SCHEMA_STATEMENTS`，接进 `db/bootstrap.ts`），并新增 `db/migrations/2026-09-03-report-final.sql` 供生产手工执行（写法与 `db/migrations/2026-09-02-final-version.sql` 一致：`BEGIN`/`COMMIT`、`IF NOT EXISTS`、RLS 收口、头部注释说明不要用 `db:migrate`）。

```sql
CREATE TABLE IF NOT EXISTS report_final_versions (
  id TEXT PRIMARY KEY,
  report_id TEXT NOT NULL UNIQUE REFERENCES reports(id),
  status TEXT NOT NULL DEFAULT 'OPEN' CHECK (status IN ('OPEN', 'DONE')),
  done_at TIMESTAMPTZ,
  done_by_user_id TEXT REFERENCES users(id),
  done_by_name TEXT,
  origin_payload_json JSONB NOT NULL,   -- 创建时的起点：空白初始标注（emptyReportAnnotation），溯源里没有"原稿"这一行的报告除外见 3.3
  payload_json JSONB NOT NULL,
  content_hash TEXT NOT NULL,
  revision INTEGER NOT NULL DEFAULT 1 CHECK (revision > 0),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 汇入记录：每一条都是「某处的一次修改」，溯源视图与"未纳入"都从这里读。
-- 与视频侧 analysis_final_intakes 的唯一结构差异：没有 change_set_id 列——
-- 报告没有客户端变更集，幂等性天然由整份 payload 保存自带的 revision
-- 乐观锁提供（同一 revision 只可能成功保存一次，见 3.4/3.5），不需要额外
-- 的去重键。kind 多了 INSERT_MODULE/INSERT_UNIT/INSERT_BLOCK/REMOVE_MODULE/
-- REMOVE_UNIT/REMOVE_BLOCK/SPAN，去掉了视频专属的 *_GROUP/*_SHOT 命名。
CREATE TABLE IF NOT EXISTS report_final_intakes (
  id TEXT PRIMARY KEY,
  final_id TEXT NOT NULL REFERENCES report_final_versions(id),
  report_id TEXT NOT NULL REFERENCES reports(id),
  seq BIGSERIAL NOT NULL,                -- 产生顺序；采纳与溯源都按它排
  kind TEXT NOT NULL CHECK (kind IN (
    'FIELD', 'INSERT_MODULE', 'INSERT_UNIT', 'INSERT_BLOCK',
    'REMOVE_MODULE', 'REMOVE_UNIT', 'REMOVE_BLOCK', 'SPAN'
  )),
  target_key TEXT NOT NULL,              -- FIELD/INSERT/REMOVE 用 module:<id> / unit:<id> / block:<id> / background.<field> / strategy.<field> / page:<n>:<field>；SPAN 用 module:<id> / unit:<id>
  target_label TEXT NOT NULL DEFAULT '',
  value_json JSONB NOT NULL,             -- 见 3.1 各 kind 的形状
  source TEXT NOT NULL CHECK (source IN ('VERSION', 'FINAL_DIRECT')),
  source_version_id TEXT REFERENCES report_versions(id),
  source_version_number INTEGER,
  actor_user_id TEXT NOT NULL REFERENCES users(id),
  actor_name TEXT NOT NULL,
  applied BOOLEAN NOT NULL,
  applied_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS report_final_intakes_final_seq_idx ON report_final_intakes (final_id, seq);
CREATE INDEX IF NOT EXISTS report_final_intakes_final_target_idx ON report_final_intakes (final_id, target_key);

-- 「基于集成版」手动创建版本的标记（同视频侧 analysis_versions.base_is_final）：
-- 集成版的 id 不在 report_versions 里，base_version_id/number 只能记 null，
-- 靠这一列区分「无基版（报告的第一版）」与「基于集成版」。
ALTER TABLE report_versions ADD COLUMN IF NOT EXISTS base_is_final BOOLEAN NOT NULL DEFAULT false;

-- 评论表去外键：集成版的 id 不在 report_versions 里，旧约束会挡住写在集成版
-- 上的评论。服务端改为自行校验 version_id 属于该报告（普通版本或集成版），
-- 同视频侧 lib/case-review-server.ts 的 requireCommentVersionOfVideo 写法。
ALTER TABLE report_version_comments DROP CONSTRAINT IF EXISTS report_version_comments_version_id_fkey;

ALTER TABLE report_final_versions ENABLE ROW LEVEL SECURITY;
ALTER TABLE report_final_intakes ENABLE ROW LEVEL SECURITY;
-- 运行时只经服务端的 BYPASSRLS 连接访问；开启 RLS 且不建策略，
-- 等于关闭 anon/authenticated 的 PostgREST 通路，不影响任何既有查询。
-- 与 db/final-version-schema.ts / db/report-schema.ts 末尾一致，此处从略。
```

主键 `report_version_comments (version_id, target_key)` 不变。评分表 `report_version_ratings` 不动，仍然只挂普通版本（集成版不评分，同视频侧 §5）。

`db/bootstrap.ts` 在 `REPORT_SCHEMA_STATEMENTS` 之后追加 `...REPORT_FINAL_SCHEMA_STATEMENTS`（顺序同视频侧 `FINAL_VERSION_SCHEMA_STATEMENTS` 排在 `REPORT_SCHEMA_STATEMENTS` 之后——`report_final_versions` 引用 `reports(id)`，必须晚于报告主表建表语句）。

## 三、汇入算法（`lib/report-final-version.ts`，纯函数部分必须可单测）

### 前言：为什么算法形状与视频侧不同

视频侧的汇入源头是**客户端算好的字段级变更集**（`V04Change[]`），报告侧**没有这种东西**——`saveReportVersion` 每次保存提交的是整份 `ReportAnnotation`，服务端只做「乐观锁 + 结构校验 + 整体覆盖写」（`lib/report-version-chain.ts` 顶部注释）。因此汇入记录不能像视频那样从"这次保存自带的变更集"里直接读，必须由服务端拿这一版**保存前**的 payload 和**保存后**的 payload，跑一遍纯函数 `diffReportAnnotation(before, after)` 现算出来。这是本规格与视频侧唯一的架构级差异，下面每一节都会指出它的连锁影响。

### 3.1 `diffReportAnnotation(before, after): ReportFinalIntakeDraft[]`

对比两份 `ReportAnnotation`，产出汇入记录草稿。顺序固定：**REMOVE → INSERT → SPAN → FIELD**（视频侧是 REMOVE → INSERT → FIELD，报告在中间插入 SPAN 这一档，因为页范围变化必须在"容器还在不在"确定之后、"容器里具体字段写了什么"确定之前处理——一个新建的模块要先有它自己的页范围，字段才有意义）。

**REMOVE（先模块，后单元，再组块）**

- `before.modules` 有、`after.modules` 无的模块 id → `REMOVE_MODULE`，`target_key = module:<id>`，`target_label = 模块名或"模块"`，`value_json = {}`。
- 两边都有的模块下，`before.units` 有、`after.units` 无的单元 id（含被删模块自己带走的单元——但那些已经被 REMOVE_MODULE 隐含覆盖，不再单独出 REMOVE_UNIT，避免落地时对着一个已经不存在的模块重复删单元）→ `REMOVE_UNIT`，`target_key = unit:<id>`，`value_json = {}`。
- 每一页 `before.blocks` 有、`after.blocks`（同页码）无的组块 id → `REMOVE_BLOCK`，`target_key = block:<id>`，`value_json = {}`。

**INSERT（先模块，后单元，再组块；不需要 `afterId`）**

报告的模块/单元/组块显示顺序**始终由页码位置推导**（`sortedModules`/`sortedRootUnits`/`sortedChildUnits` 按 `firstPageNo` 排序，`sortBlocksByPosition` 按 `(y,x)` 排序），数组自身的插入位置从不影响任何展示或校验——这与视频侧镜头/桥段数组顺序即权威顺序完全不同，因此报告的 INSERT 记录**不需要** `afterId`/`parentGroupId`，落地时直接 `push` 进数组末尾即可：

- `after.modules` 有、`before.modules` 无的模块 → `INSERT_MODULE`，`target_key = module:<id>`，`value_json = { item: ReportModule }`。**此时模块还没有页**（页范围由紧跟着的 SPAN 记录建立），落地顺序上 INSERT 必须先于 SPAN。
- 两边都有的模块下新增的单元，以及新模块自带的单元 → `INSERT_UNIT`，`target_key = unit:<id>`，`value_json = { item: ReportUnit }`（`item.mid`/`item.pid` 随对象一起写入，落地时校验 `mid` 指向的模块、`pid`（非空时）指向的单元必须已经存在，否则 NOOP）。
- 每一页新增的组块 → `INSERT_BLOCK`，`target_key = block:<id>`，`value_json = { item: ReportBlock, pageNo: number }`。

**SPAN（模块先于单元；只对"直属页集合"变化的容器出记录）**

对 `after` 里仍然存在的每个模块/单元（新插入的也算），比较它在 `before`／`after` 两份 payload 里的**直属**页集合（`openPagesOf` 语义：模块取 `p.mid===id && !p.uid`，单元取 `p.uid===id`；不含被嵌套单元占用、只在展示时才下钻的那些页——嵌套单元自己会单独出一条 SPAN）。集合不同（含"从无到有"，即新建容器的初始页范围）→ 一条 `SPAN`，`target_key = module:<id>` 或 `unit:<id>`，`target_label = 名称或类型标签`，`value_json = { pageNumbers: number[] }`（升序排列，**是这个容器的全部新直属页，不是增量**——整段替换，同 FIELD 语义，理由见 3.2）。

**FIELD（背景与资料 → 策略 → 模块字段 → 单元字段 → 页字段 → 组块字段，同一层内按 id/页码升序，纯粹为了产生确定性顺序，不影响正确性）**

逐字段比较，不同则各出一条 `FIELD` 记录，`value_json = afterValue`：

| 容器 | 字段（`target_key`） | 值类型 |
|---|---|---|
| 背景与资料 | `background.city` / `background.developer` / `background.projectBackground` / `background.businessBackground` | 字符串 |
| 竞争与提报策略 | `strategy.narrative` / `strategy.model` | 字符串 |
| 模块（`module:<id>:<field>`） | `name` / `rel` / `role` | 字符串 |
| 单元（`unit:<id>:<field>`） | `name` / `rel` / `task` / `role` / `psy` / `concl` | 字符串 |
| 页（`page:<n>:<field>`） | `func` / `org` / `transition` | 字符串／布尔 |
| 组块（`block:<id>:<field>`） | `name` / `type` / `style` / `rel` / `roles` / `narr` / `mark` | 字符串／字符串数组；`x`/`y`/`w`/`h` 也纳入比较（当前 UI 没有创建后再拖拽/缩放组块的入口，理论上不可能触发，但比较逻辑不为此特殊处理，统一按"值不同就出一条"处理，成本为零） |

**target_label**：模块/单元/页/组块字段沿用 UI 里已经在用的中文标签（`ReportSectionPopover`/`ReportPageModal` 里 `DeckCommentEntry` 的 `targetLabel` 拼法，如"模块 1·名称""讲述单元 1-2·讲述作用""第 5 页·页面作用""第 5 页·组块 2"）；SPAN 的 `target_label` 用容器名称或"未命名模块/单元"。

**NOOP 前置说明**：3.1 只负责"diff 出记录"，不判断落地时是否成功——同一条记录在不同时刻落地（普通保存立即应用 vs 采纳时事后应用）可能因为目标已经被别人删除而失败，NOOP 的判定统一放在 3.2。

### 3.2 一条汇入记录落到 payload（`applyReportFinalIntake(payload, intake) → { payload, effect: "APPLIED" | "NOOP" }`）

- `REMOVE_MODULE`：id 不存在 → NOOP；存在则调用（复用）`removeModule` 语义：模块与其全部单元一并删除，原直属这些容器的页退回未归入。
- `REMOVE_UNIT`：id 不存在 → NOOP；存在则调用（复用）`removeUnit` 语义：子单元提升给它的父级，直属页退给父级（父级为空则退给模块）。
- `REMOVE_BLOCK`：id 在任何页都找不到 → NOOP；找到则从所在页的 `blocks[]` 里删除。
- `INSERT_MODULE`：id 已存在 → NOOP；否则 `push` 进 `modules[]`（此时它还没有页，等紧随其后的 SPAN 记录落地）。
- `INSERT_UNIT`：id 已存在于 `units[]` → NOOP；`item.mid` 指向的模块不存在 → NOOP；`item.pid` 非空且指向的单元不存在 → NOOP；否则 `push` 进 `units[]`。
- `INSERT_BLOCK`：id 已存在于任何页的 `blocks[]` → NOOP；`pageNo` 在 payload 里找不到对应页 → NOOP；否则 `push` 进该页的 `blocks[]`。
- `SPAN`：`target_key` 指向的模块/单元不存在 → NOOP（典型场景：这条 SPAN 来自一个后来被删除的容器，落地顺序上 REMOVE 已经先处理，这里自然扑空）；否则执行「设置直属页归属」：
  1. 对 `value_json.pageNumbers` 里的每一页 `p`：无论 `p` 当前挂在谁名下，一律先摘掉（`mid=null,uid=null`），再按 `target_key` 的种类赋值——`module:<id>` → `p.mid=id, p.uid=null`；`unit:<id>` → 找到该单元的 `mid`，`p.mid=该值, p.uid=id`。
  2. 赋值全部完成后，跑一遍收拢：（a）深度优先，先处理最深层的单元，逐级向上，若某单元的 `unitPages`（直属+嵌套）不连续，只保留**含最小页码那一段连续游程**，其余页退回它的直接上级（父单元存在则退给父单元，否则退给模块——不直接摔到"未归入"）；（b）单元处理完毕后处理模块：若某模块的 `modulePages` 不连续，只保留含最小页码那段连续游程，其余页退回"未归入"（`mid=null,uid=null`，模块之上没有更高一级容器）；（c）任何模块/单元处理后若变空（`modulePages`/`unitPages` 为空且单元没有子单元），按 `applyMove` 现有语义整体撤销该容器（模块连带其单元一起撤销）。这一步是 `applyMove` 收拢逻辑的直接复用/下沉——建议把 `applyMove` 里"清理死段"的那段循环抽成 `pruneEmptyStructure(payload)` 共享给两处调用，避免两份实现日后走样。
  3. NOOP 判定与 FIELD 一致：收拢完成后跑 `validateReportAnnotation`，不通过则整条 SPAN 记为 NOOP，`payload` 回退到应用前（同 3.2 通用规则最后一条）。
- `FIELD`：定位目标——`background.*`/`strategy.*` 直接按字段名取；`module:<id>:<field>`/`unit:<id>:<field>` 按 id 找到对应对象；`page:<n>:<field>` 按页码找到对应页；`block:<id>:<field>` 遍历所有页找到对应组块。目标不存在（模块/单元/组块已被别人删除、或极端情况下 `<n>` 引用了不存在的页码——理论不可能，防御性处理）→ NOOP；否则写入 `afterValue`。
- **落库前统一跑 `validateReportAnnotation(next, pageNumbers)`**：不通过则该条记为 `NOOP`，`payload` 保持应用前的样子——**绝不能让别人的保存因为集成版失败**（同视频侧 3.2 最后一条铁律）。
- `NOOP` 也算 `applied = true`（它已被处理，只是无处可落）。

### 3.3 集成版的创建与回填（`ensureReportFinalVersion`）

**与视频侧的关键差异**：视频侧靠重放 `collaboration_revision_events`（细到每一次编辑的事件流水）来精确重建历史；报告侧**没有这张表**——`report_versions` 每一行只保留"当前 payload + 这一版创建时固化的 `base_payload_json` 快照"，版内多次保存互相覆盖、不留痕迹。回填算法因此只能做到"版级粒度"，不是"字段编辑级粒度"，具体如下：

- 起点 `origin = emptyReportAnnotation(pageNumbers)`（报告刚转换完、还没有任何人标注时的空白状态——这是报告真正唯一确定的"原稿"，不像视频侧 v1 那样需要用 `deriveFinalOrigin` 倒放推算）。
- 取该报告**全部** `report_versions` 行，按 `updated_at ASC`（并列按 `id` 兜底排序）排出一个顺序。
- 对每一行 `V`：`before = V.base_payload_json`（`V` 是报告第一版、没有基版时 `before = origin`），`after = V.payload_json`；跑 `diffReportAnnotation(before, after)`，产出的每条记录都归属到 `V`（`source_version_id = V.id`、`source_version_number = V.version_number`、`actor = V` 的 owner），统一打上 `V.updated_at` 作为这批记录的时间戳，按 3.1 的顺序追加进总账本。
- 按上面排出的版本顺序，依次把每一版的记录追加进账本、依次用 3.2 应用到累积中的 payload 上，得到集成版的初始 `payload_json` 与完整的 `report_final_intakes` 记录集。
- 首次持久化的时机：`saveReportVersion` 内（事务中，validate 通过、即将写库之前）。**GET 不落库**（同视频侧 3.3 的守卫，报告侧也要补一条等价测试）：读取时若集成版不存在，用同一纯函数在内存里算出虚拟集成版（`isVirtual: true`，`id` 为 `null`）。
- 新报告：报告第一版落库时不必同时建集成版；第一次保存后走上面的路径即可（与视频一致）。

**已知局限（版级粒度而非字段编辑级粒度）**：如果版本 A（无基版，或基于某个更早的基版）在集成版**创建之前**就已经存在，且它的 owner 在集成版创建之后仍然继续编辑 A、每次都重新保存整份内容，那么 A 在"回填批次"里的那一条 diff（`base_payload_json → 当时的 payload_json`）只覆盖到"回填发生那一刻 A 的状态"，之后 A 的每一次新保存都会走 3.4 的增量路径（精确、无歧义）。真正有歧义的场景**只发生在回填这一次性动作本身**：如果 A 在被回填之前，就已经对同一个字段做过"改了又改回去""改了又改成别的值"这类**版内自我覆盖**，回填只能看到 A 当时保存的**最终**内容，看不到 A 版内的中间状态与真实修改时刻——这在效果上等价于"把 A 从创建到回填这段时间里的所有编辑，都算作发生在 A 最后一次保存的那个时间点"。多数情况下这不影响"按处取最新"的正确性（因为我们关心的是"最终值"而非"中间过程"），唯一会失真的情形是：A 创建后，B 基于 A 的某个中间状态 fork 出去并修改了某字段，随后 A 自己又把同一字段改成第三个值并保存——真实时间顺序是"A 中间态 → B 改字段 → A 最终态"，回填后的记录顺序会是"A（整版，含该字段最终值，打上 A 的 `updated_at`）先出现还是 B 先出现"完全取决于两者 `updated_at` 谁更晚，如果 A 的 `updated_at` 确实晚于 B（这是真实发生的先后关系），排序仍然正确；只有在**极端时钟/记录误差**下才会错序。综合评估：这个局限只影响"集成版第一次被创建之前就已经存在多版交叉编辑历史"的报告，且哪怕命中也大概率给出正确结果，遗留问题已经列进七、待定问题，建议按当前设计先上线，后续如证实频繁命中再补齐。

### 3.4 普通版本保存时的汇入（改 `saveReportVersion`）

在 `lib/report-version-chain.ts` 的 `saveReportVersion` 里，`validateReportAnnotation` 通过、且内容确有变化（`nextHash !== mine.content_hash`，或首次创建版本）之后、写库的同一事务内：

- **更新既有版本**（`mine` 分支）：`before = mine.payload_json`（这一版保存前的内容，不是 origin，不是 base——是它自己上一次的内容，因此天然精确，不受 3.3 的粒度局限），`after = validated.value`。
- **首次创建版本**（无 `mine` 分支）：`before = baseRow ? basePayload : emptyReportAnnotation(pageNumbers)`，`after = validated.value`——与该版本自己的 `base_payload_json` 定义完全一致，这也是为什么 3.3 回填时直接复用 `base_payload_json` 做 `before` 是自洽的。

之后：`ensureReportFinalVersion` → `diffReportAnnotation(before, after)` → 若集成版 `status='OPEN'` 逐条按 3.2 应用并写 `applied=true, applied_at=now`，更新集成版 `payload_json`/`content_hash`/`revision`/`updated_at`；若 `DONE` 只写记录 `applied=false`。

**幂等性**：不需要额外的去重键（对照视频侧靠 `change_set_id + source_version_id` 去重）——`saveReportVersion` 本身已经用 `revision` 做乐观锁，同一个 `(versionId, revision)` 只可能成功走到"写库"这一步一次；一次网络重试如果撞上"第一次已经成功"，会在 `revision` 校验那一步就拿到 `REVISION_CONFLICT` 而根本不会进到汇入逻辑，天然不会重复写汇入记录。这是报告侧因为"整份 payload + revision 乐观锁"架构而**比视频侧更简单**的一点，明确记录在案，不是遗漏。

`ReportSaveResult` 增加 `finalIntake: { merged: boolean; pending: number }`（`merged` 指本次进入了集成版；`pending` 是集成版当前未纳入总数），前端据此出 toast（同视频侧五、17）。

### 3.5 老孙直接编辑集成版（`saveReportFinalVersionDirect`）

与视频侧走"变更集 + `change_set_id` 去重"不同，报告侧集成版的直接编辑复用报告自己的整份 payload + revision 乐观锁模型，不需要额外的幂等键：

- 入口：`PUT /api/reports/[id]/annotation`，请求体 `versionId === "final"`（新增的哨兵值，与视频侧 `basedOnVersionId: "final"` 的哨兵用法对应；PUT **不改形状**，只是 `versionId` 多接受这一个特殊字符串）。非老孙 → 403，错误信封同现有 `{error, code:"FORBIDDEN"}`。
- 校验 `input.revision` 等于 `report_final_versions.revision`（不等 → `REVISION_CONFLICT`，与普通版本保存同一错误码与前端处理路径）。
- `validateReportAnnotation(input.payload, pageNumbers)` 不通过 → `VALIDATION_FAILED`（同普通保存）。
- 通过后：`before = 集成版当前 payload_json`，`after = validated.value`，若内容哈希未变则直接返回 `changed:false`（不写汇入记录）；否则整份覆盖写入集成版（`revision+1`），并用 `diffReportAnnotation(before, after)` 拆出汇入记录，`source='FINAL_DIRECT', source_version_id=null, applied=true`（这里不是"靠汇入应用变更"，变更已经直接生效——记录只是为了让溯源视图显示"集成版·直接修改"，与视频侧 3.5 后半段同一逻辑）。
- 返回 `ReportSaveResult` 同形状：`version` 字段是集成版的 `ReportCurrentVersion`-同构对象（`id=集成版id`，`number=0`，`ownerUserId=""`，`ownerName="集成版"`，`baseNumber=null`，`isMine=false`，`isFinal=true`），外加 `finalIntake`。

### 3.6 定稿／取消定稿／采纳（同视频侧 3.6，函数改名对应）

- `setReportFinalVersionStatus(db, actor, { reportId, status })`：仅老孙。`DONE` 时写 `done_at`/`done_by_*`；`OPEN` 时清空。
- `adoptReportFinalIntakes(db, actor, { reportId, intakeIds?: string[]; all?: boolean })`：仅老孙。目标记录必须 `applied=false`；按 `seq` 升序逐条应用（3.2），写 `applied=true, applied_at`。两态下都允许采纳。
- 以上都写一条 `insertAudit`（动作名 `REPORT_FINAL_STATUS_CHANGED` / `REPORT_FINAL_INTAKE_ADOPTED` / `REPORT_FINAL_SAVED`，命名与视频侧的 `V19_FINAL_*` 平行）。

### 3.7 SPAN 冲突示例（≥3 个，均带页号）

以下例子里，「M1」「M2」是模块，「U1」是单元，页号用 `p01`…表示；箭头表示"按 seq 顺序依次应用的 SPAN 记录"。

**示例一：两个版本把同一页分别划给不同模块（后改覆盖先改，简单情形）**

- 初始：M1 直属 `p01–p05`，M2 直属 `p06–p10`。
- v2（老王）把 `p05` 从 M1 拖进 M2：产生 `SPAN(M1, {p01,p02,p03,p04})` 与 `SPAN(M2, {p05,p06,…,p10})`，seq=10/11。
- v3（老李，基于集成版创建之前更早的快照，不知道 v2 的改动）把 `p05` 拖回 M1（他看到的世界里 `p05` 还在 M1）：实际上他的完整保存内容里 M1 直属仍是 `{p01..p05}`，产生 `SPAN(M1, {p01,p02,p03,p04,p05})`，seq=20（M2 因为这一版没碰它，不产生 SPAN(M2,...)）。
- 回放：先应用 seq=10 的 `SPAN(M1,{p01..p04})`——`p05` 此时仍属于谁由更早的记录决定（初始状态），先摘除后按记录赋值；再应用 seq=11 的 `SPAN(M2,{p05..p10})`——`p05` 归 M2；再应用 seq=20 的 `SPAN(M1,{p01..p05})`——`p05` 被摘出 M2、归回 M1。
- **结果**：`p05` 最终归 M1（seq=20 是最后一条动到 `p05` 的记录，后改覆盖先改），M2 变成 `{p06..p10}`（M2 上一次的记录 seq=11 里包含 p05，但 p05 已经被后来的 M1 记录摘走，M2 的"当前有效集合"是 `{p06..p10}`，不需要 M2 自己再出一条新 SPAN——摘除是隐式的，不用记账）。

**示例二：一页被踢出两层嵌套，波及父单元与祖父模块的连续性**

- 初始：M1 直属 `p01,p04,p05`（不含 p02,p03——它们归 U1），U1（`mid=M1`）直属 `p02,p03`；`unitPages(U1)={p02,p03}`，`modulePages(M1)={p01..p05}` 整体连续。
- v2 把 `p03` 单独拖出 U1、拖进另一个模块 M2：产生 `SPAN(U1, {p02})`（U1 直属收缩为只剩 p02）与 `SPAN(M2, {…, p03, …})`。
- 回放后：U1 直属变成 `{p02}`（连续，合法，不用收拢）；M1 的 `modulePages` 变成 `{p01,p02,p04,p05}`（p02 仍归 U1，U1 仍在 M1 下，算 M1 的一部分）——**不连续**（缺 p03，它已经被 v2 明确划给 M2，这不是冲突，是正常的"这页现在真的不归 M1 了"）。
- 收拢规则介入：`modulePages(M1)` 不连续 → 保留含最小页码的那段连续游程 `{p01,p02}`，其余 `{p04,p05}` 退回"未归入"（因为它们和 `{p01,p02}` 之间隔着已经不属于 M1 的 p03，两段散落，M1 上面没有更高容器可退，只能退到未归入的自由页区）。
- **结果**：M1 = `{p01,p02}`（U1 仍嵌在里面，`{p02}`），`p04,p05` 变成未归入页，等着有人手动重新划分；M2 正常拿到 `p03`。这个例子说明"页被后来的记录划走"可能连带产生原容器不连续、进而触发收拢丢页，是设计上接受的代价（同一时间有两个人在编辑同一份报告结构本来就存在这种风险，收拢规则保证的是"永远落在一个合法状态"，不保证"零丢失"）。

**示例三：单元被删除，其父单元/模块的直属页判定要等 REMOVE 先处理完**

- 初始：M1 直属 `p01,p06`，U1（`mid=M1,pid=null`）直属 `p02,p03`，U2（`mid=M1,pid=U1`，U1 的子单元）直属 `p04,p05`。
- v2 删除 U1（`REMOVE_UNIT(U1)`，seq=10）：按 3.2，U2 提升为 M1 的根单元（`pid=null`），U1 的直属页 `{p02,p03}` 退给它的父级——U1 没有父单元（`pid=null`），所以退给模块 M1；U1 自己从 `units[]` 里消失。
- 同一份保存里，v2 还把 `p03` 挪去了别的地方，产生 `SPAN(M1, …)` 覆盖 M1 新直属集合、`SPAN(某个别的容器, {…p03…})`——这些记录 seq 都在 REMOVE_UNIT 之后（3.1 顺序：REMOVE 先于 SPAN）。
- **结果**：回放时先执行 `REMOVE_UNIT(U1)`（U2 提升、U1 直属页临时并入 M1），再执行 SPAN 记录做最终页归属调整——如果颠倒顺序（SPAN 先于 REMOVE），SPAN 记录里出现的"U1 的原直属页该归哪"会因为 U1 还没被摘除而计算错误（可能把本该退给 M1 的页错误地当成还需要"从 U1 摘除"的页，多绕一层）。这正是"REMOVE 必须先于 SPAN"这条顺序规则要防的问题，示例三专门验证这一点。

## 四、接口

### 4.1 `GET /api/reports/[id]/annotation`

响应 `ReportVersionChain` 增加：

```ts
final: {
  id: string | null;            // 虚拟时为 null
  status: "OPEN" | "DONE";
  doneAt: string | null;
  doneByName: string | null;
  updatedAt: string;
  pendingCount: number;         // applied = false 的记录数
  isVirtual: boolean;
} | null;                       // 报告尚无真实版本时为 null
```

- `?version=final` → `current` 返回集成版：`ReportCurrentVersion` 形状不变，附加 `isFinal: true`，`id` 为集成版 id（虚拟时 null），`number: 0`，`ownerName: "集成版"`，`ownerUserId: ""`，`baseNumber: null`，`basePayload: null`，`isMine: false`。同时响应多带 `finalTrace: { originPayload: ReportAnnotation; intakes: ReportFinalIntake[] }`，`ReportFinalIntake = { id, seq, kind, targetKey, targetLabel, value, source, sourceVersionNumber, actorName, applied, createdAt }`（形状与视频侧 `V19FinalIntake` 一一对应）。
- 不带 `?version` 时：`final` 存在（含虚拟）→ `current` 即集成版；否则原规则（`resolveReportDefaultVersion`）。
- 老孙可编辑集成版：集成版视角下 `chain.current.isMine` 恒为 `false`，前端的 `readOnly` 改按 `isFinalView ? !isCaseReviewer(viewerName) : !chain.current.isMine` 计算（见五、16）。
- 类型放 `lib/report-final-ui-model.ts`（或直接扩进 `lib/report-version-chain.ts`，与 `ReportVersionChain` 同处——待定，见七）。

### 4.4 评论 `GET/POST /api/reports/[id]/review`

`lib/report-review-server.ts` 补齐"集成版也是合法版本锚点"这一件事，做法完全照抄视频侧 `case-review-server.ts` 已经验证过的写法：

- `saveReportReviewComment` 改走 `requireCommentVersionOfReport`。
- `stars`/`canRate` 规则不变：集成版不在 `report_versions` 里，天然落入"找不到就是不能评分"，不需要新增判断分支。
