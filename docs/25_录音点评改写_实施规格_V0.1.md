## 一、目标与真实场景

老孙在线下分享会上逐个点评大家的作业，并现场录音。会后他把某一份作业的点评录音传到工作台上，挂在被点评的那一版上。系统先转写录音，再理解点评内容，然后在这一版的快照上改写出一个**点评版**。点评版供作者和其他同事对照学习，老孙也可以在溯源视图里把其中的写法采纳进集成版。

点评往往不是逐条的：既有「井盖里钻出来的是警察」这种点名到一处的**具体意见**，也有「母题看浅了」「关键创意描述都在复述画面」这种**总体意见**。AI 必须把总体意见落实到所有受影响的条目，不能只改点名提到的地方。

## 二、冻结的产品口径

1. **入口只给老孙**：判定方式沿用 `isCaseReviewer`（显示名「老孙」）。他看**别人的普通版本**时，页头右侧、版本胶囊之前出现「上传点评录音」。看集成版、点评版或自己的版本时不出现。
2. **一份作业只有一个点评版**：一段录音只点评一个人的一版作业。生成之前，老孙可以重新上传或放弃；生成之后，这一版的入口变成「查看点评版 vN」，不能再传。
3. **处理在后台跑**：上传 → 转写成文字 → 理解点评、拟定改动（界面显示 3 步）。期间页面照常可用；离开页面也不中断，回来能接上。处理完用共用 toast 提示，入口变成「点评改动待确认 · N 处」。失败时入口变成「点评录音处理失败」，可以重试或重新上传。
4. **先确认再生成**：确认面板按「意见」组织。每条意见标明总体或具体，附老孙的原话和时间点（点时间点可跳到录音对应位置），下面列「原 → 改」。每处改动能单独取消，整条意见也能整条取消。两条意见改到同一处时只列一处，并标「同时依据意见 X」。**没落到条目的话**（夸奖、闲聊、被点评人的解释、别人的提问、做法建议）单独列出并写明原因。面板底部是完整文字稿（区分说话人；按词表校正过的听写用虚线下划线标出）。
5. **点评版是一种新的版本类型**：
   - 编号接着排；**不占任何人的版本名额**；
   - 标签为「vN 老孙录音点评 基于 vM」，版本菜单里挂在被点评版本的下面，带「点评版」标记；
   - 「对比基版」的基版是**上传那一刻**被点评版本的快照；
   - 页面顶部有点评录音卡：录音播放、意见清单（每条显示落实了几处，点击跳到第一处）、完整文字稿。点评版、录音和文字稿**全站可见**；待确认的拟定改动只有老孙看得见。
6. **编辑按普通版本的规则**：老孙是点评版的归属人，可以直接修改其中任何内容，包括插入镜头和桥段，失焦即自动保存。其他人在点评版上动手，和改别人的版本一样：已有自己版本的，改动进自己的版本；还没有版本的，以点评版当时的内容为底新建自己的版本。点评版本身只有老孙改得动。
7. **不自动汇入集成版**。在集成版的溯源视图里，凡是点评版改过的条目，都多一行「点评版 vN 的写法」，老孙可以逐条「采纳」（见第六节）。
8. **点评版不打分**（它不是谁的作业），和集成版一样。条目评论照旧：只有老孙能写，展示跨版本汇总，版本标签写「vN（点评版）」。
9. **比较默认开启**：从入口、提示条或生成后进入点评版时自动打开「比较」。每处改动除了显示「vM 原文」，还多一枚「依据 意见 N」标记，悬停可见意见摘要。老孙手改过的地方另标「老孙已手改」。
10. **被点评版本上的提示条**：点评版生成后，在被点评版本的视频下方显示「老孙对这一版做了录音点评，据此生成了点评版 vN（K 处改动）。这一版保持原样。〔去看点评版〕」，所有人可见。
11. **AI 只读文字，看不到视频**：它可以改写文字条目、在词表内换选项、改整体创意评价、补写老孙口头说出的画面信息。它**不增删桥段和镜头、不改时间码**。点评里要求补镜头的话，记进「没落到条目的话」，提醒人工去补。

## 四、处理流水线

### 4.1 状态

```
UPLOADING ──UPLOADED──▶ TRANSCRIBING ──▶ UNDERSTANDING ──▶ PENDING_CONFIRM ──CONFIRM──▶ GENERATED
    │                        │                  │                  │
    └────────────────────────┴──────────────────┴──────────────────┴──ABANDON──▶ ABANDONED
                             └──失败──▶ FAILED(failed_step) ──RETRY──▶ 回到失败的那一步
```

- `GENERATED` 和 `ABANDONED` 是终态。`FAILED` 不是终态：可以重试，也可以放弃。
- 「重新上传」就是放弃当前任务，再新建一个。

### 4.2 接口（都挂在 `/api/videos/[id]/audio-reviews` 下）

1. `POST /api/videos/[id]/audio-reviews`：`{ baseVersionId: string | null, fileName, contentType, sizeBytes }` → 201 `{ review, uploadUrl }`。
   - 依次检查：同源 → 登录 → 老孙；是否已配置（4.7）；基版存在、属于该视频、是 `PERSONAL`、不归老孙；这一版没有在途或已生成的点评。
   - `baseVersionId` 为 null 表示被点评的是虚拟 v1，先在同一事务内按 `materializeV19FirstVersion` 物化。
   - `contentType` 必须以 `audio/` 开头，或属于腾讯云支持的扩展名（m4a/mp3/wav/aac/flac/ogg/amr/wma/3gp/mp4）；大小不超过 500MB。
   - 对象键为 `audio-reviews/<reviewId>/original`，预签名 PUT 有效期 900 秒。
2. `GET /api/videos/[id]/audio-reviews/[reviewId]` → `{ review }`（`AudioReviewView`，4.8）。
   - 老孙能看到任何状态；其他人只能看 `GENERATED`，其余状态回 404。
   - 任务未到终态且租约空闲时，用 `after()` 推进一次（4.3）。返回头 `Cache-Control: no-store`。
3. `POST /api/videos/[id]/audio-reviews/[reviewId]`：`{ action: "UPLOADED" | "RETRY" | "ABANDON" | "CONFIRM", selectedChangeIds? }` → `{ review, reviewVersionId? }`。只有老孙能调。
   - `UPLOADED`：先 HEAD 核对对象和大小，再提交转写，状态进 `TRANSCRIBING`，然后 `after()` 推进。
   - `RETRY`：仅 `FAILED` 可用，回到失败的那一步，然后 `after()` 推进。
   - `ABANDON`：仅非终态可用。
   - `CONFIRM`：见 4.9。
4. `GET /api/videos/[id]/audio-reviews/[reviewId]/audio` → 307 跳转到预签名 GET（3 小时），可见性同第 2 条。供 `<audio src>` 使用。

以上路由都写 `export const maxDuration = 300`。检查顺序照仓库惯例：同源 → 登录 → 业务；`tests/` 里用读源码的方式断言顺序。

### 4.3 推进（`advanceAudioReview(db, reviewId, { deadline })`）

- **触发点**：`UPLOADED`、`RETRY` 之后，以及每次 GET 时，都用 `after()` 调用；`deadline` 取「请求开始 + 280 秒」。前端在页面可见时每 4 秒 GET 一次。
- **租约**：先执行 `UPDATE audio_reviews SET lease_until = now() + interval '290 seconds' WHERE id = ? AND status IN (...) AND (lease_until IS NULL OR lease_until < now()) RETURNING ...`，拿不到就直接返回。每推进完一步写 `updated_at`；退出时清空租约。
- **TRANSCRIBING**：每 4 秒调一次 `DescribeTaskStatus`，直到成功、失败或时间不够。成功后把结果解析进 `transcript_json`，状态改为 `UNDERSTANDING`，并在同一次调用里接着往下走。
- **UNDERSTANDING**：只有剩余时间 ≥ 245 秒才开始调模型（否则留给下一次 GET）。模型调用超时 240 秒。返回空内容、JSON 不合法或校验后一处可用改动都没有，算一次失败。`llm_attempts` 小于 2 时自动再试，否则转 `FAILED(UNDERSTAND)`。成功后写入 `proposal_json`、`proposed_at`、`llm_*` 和 `input_content_hash`，状态改为 `PENDING_CONFIRM`。
- 所有外部错误都转成中文 `fail_reason`，绝不往外抛（参照 `report-converter.ts`）。

### 4.4 转写（腾讯云录音文件识别，`lib/audio-review/tencent-asr.ts`）

- **签名**：自己实现 TC3-HMAC-SHA256（WebCrypto），不新增依赖。主机 `asr.tencentcloudapi.com`，Version `2019-06-14`。`fetch` 可注入，便于测试。
- **CreateRecTask 参数**：
  - `EngineModelType` 取环境变量 `TENCENT_ASR_ENGINE`，默认 `16k_zh_en_2.0`（大模型 2.0，支持说话人分离）；
  - `ChannelNum=1`、`ResTextFormat=2`（带标点和词级时间）、`SourceType=0`；
  - `Url` = 预签名 GET（3 小时）；
  - `SpeakerDiarization=1`、`SpeakerNumber=0`；
  - `ConvertNumMode=1`、`FilterModal=1`；
  - `HotwordList`：工作台字段名、全部词表选项、「老孙」和被点评人姓名，每个词权重 10，最多 128 个。若接口报热词参数无效，就去掉热词再提交一次。
- **DescribeTaskStatus**：`Status` 取值 0、1、2、3。成功时读 `ResultDetail[]`，每句存成 `{ id, startMs, endMs, speakerId, text }`，`text` 取 `FinalSentence`；`audio_duration_ms` 取 `AudioDuration`。结果只在腾讯云保留 24 小时，所以成功后立即落库。
- **密钥**：优先用 `TENCENT_ASR_SECRET_ID` / `TENCENT_ASR_SECRET_KEY`；没配就复用 `COS_SECRET_ID` / `COS_SECRET_KEY`。该子账号要有 ASR 权限。
- 错误码映射成中文：下载失败、识别失败、鉴权失败、欠费、超出频率。

### 4.5 理解与改写（DeepSeek，`lib/audio-review/deepseek.ts` + `lib/audio-review/prompt.ts`）

- **调用**：`POST {DEEPSEEK_BASE_URL}/chat/completions`，`model = DEEPSEEK_MODEL`（默认 `deepseek-v4-pro`），开启思考（`thinking: {type: "enabled"}`、`reasoning_effort: "high"`），`response_format: {type: "json_object"}`，`max_tokens` 32000。`fetch` 可注入。
- **提示词版本**：常量 `AUDIO_REVIEW_PROMPT_VERSION = "2026-10-10.1"`，写进任务行。
- **输入**（一条 user 消息里的 JSON，system 消息放规则）：
  1. **字段说明**：工作台每个可改条目的含义、写法要求、格式。创意思维链用 Markdown 嵌套列表（docs/24 第三节）；选项字段列出可选词表标签。字段说明先由工程起草，**请老孙校订**。
  2. **作业**：被点评版本快照的可读结构，每个可改的位置带稳定键：`facts.<key>`、`path.primaryType`、`path.primaryDetails.<subKey>`、`path.auxiliaryTypes.<TYPE>.description|creativeRole`、`shotGroup:<id>.<field>`、`shot:<id>.<field>`。镜头给出「2-3」这样的镜号和时间码（只读）。
  3. **文字稿**：`[{ id, t: "mm:ss", speaker: "S0"…, text }]`，并告诉模型：录音者是老孙，被点评人是谁，现场可能还有别人提问。
- **要求**（写进 system）：
  - 先认出哪个说话人是老孙。老孙的话是唯一依据；被点评人的解释、别人的提问只用来理解上下文。
  - 把老孙的话归纳成意见，每条标总体或具体。
  - **总体意见要逐个检查全部条目**，凡是建立在被否定的判断上的条目都要跟着改，而不只是点名提到的那几处。
  - 改写时保留作者原有的、没被否定的信息，语气用作业本身的书面体。
  - 不增删桥段和镜头、不改时间码；选项只能用给出的标签。
  - 文字稿可能有同音错字，按词表和上下文理解；校正过的词放进 `corrections`。
  - 老孙的每段实质发言，要么被某条意见引用，要么进「没落到条目的话」并写明原因。
- **输出 JSON**（示例写进提示词）：

```json
{
  "speakers": { "reviewer": "S0", "labels": { "S1": "刘梦娜", "S2": "其他同事" } },
  "opinions": [
    { "id": "o1", "kind": "GENERAL", "summary": "…", "segmentIds": [3, 4, 6], "rationale": "落实说明：…" }
  ],
  "changes": [
    { "key": "facts.creativeMotif", "value": "…", "opinionIds": ["o1"] },
    { "key": "facts.auxiliaryMechanism", "value": { "options": ["对置生义"], "custom": "…", "advanced": "" }, "opinionIds": ["o4"] },
    { "key": "path.primaryDetails.reveal", "value": "…", "opinionIds": ["o1"] }
  ],
  "unaddressed": [ { "segmentIds": [1], "reason": "肯定的部分，不需要改" } ],
  "corrections": [ { "segmentId": 9, "from": "对质生意", "to": "对置生义" } ]
}
```

### 4.6 校验与归一（`lib/audio-review/proposal.ts`，纯函数，重点测试）

- 键必须存在于快照中，且在可改白名单内（不含 `startTime`/`endTime`、结构、`metadata`、`contract`）。键不存在或不在白名单内就丢弃这处改动，并把原因记进 `proposal_json.dropped`（不展示给老孙，留作排查）。
- 按字段类型校验取值：
  - 文字：去掉首尾空白，不能为空；
  - 评价：只能是 `S`、`A`、`B`、`C`；
  - 选项：把标签精确映射成 optionId，个数上限和互斥规则照 `assertV04PayloadContract`；
  - 承重载体：只能是「故事」「文案」「视听规则」；
  - `path.primaryType` 变了，必须同时给出新类型的全部细项，且不能和辅助路径重复。
- 改后值和快照值相同的改动丢弃；同一个键出现多次就合并，`opinionIds` 取并集。
- 意见按引用片段的最早时间排序，编号 1…N。没有任何改动的意见保留（表示听到了，但不需要改）。
- 存进 `proposal_json` 的结构：

```ts
{
  speakers: { reviewer: string; labels: Record<string, string> },
  opinions: { id; number; kind: "GENERAL" | "SPECIFIC"; summary; rationale; segmentIds: number[]; changeIds: string[] }[],
  changes: { id; key; targetKey; subKey: string | null; label; valueType; before: unknown; after: unknown; beforeText; afterText; opinionIds: string[] }[],
  unaddressed: { segmentIds: number[]; reason: string }[],
  corrections: { segmentId: number; from: string; to: string }[],
  dropped: { key: string; reason: string }[],
}
```

  其中 `targetKey` 是落库用的 V04 键：`path.primaryDetails.reveal` 归到 `path.primaryDetails`，`path.auxiliaryTypes.<TYPE>.*` 归到 `path.auxiliaryTypes`；`label` 形如「第三模块 · 主导路径细项 · 揭示／反转」。

### 4.8 `AudioReviewView`（GET 返回给前端的形状，放在 `lib/audio-review-model.ts`，客户端可用）

```ts
type AudioReviewStatus = "UPLOADING" | "TRANSCRIBING" | "UNDERSTANDING" | "PENDING_CONFIRM" | "GENERATED" | "FAILED" | "ABANDONED";
type AudioReviewView = {
  id: string; videoId: string;
  baseVersionId: string; baseVersionNumber: number; baseOwnerName: string; reviewerName: string;

  step: 0 | 1 | 2;                       // 上传录音 / 转写成文字 / 理解点评、拟定改动
  audio: { fileName: string; sizeBytes: number; durationMs: number | null; url: string };  // url 指向 4.2 第 4 条
  transcript: { segments: { id: number; startMs: number; endMs: number; speaker: string; isReviewer: boolean; text: string;
                            corrections: { from: string; to: string }[] }[] } | null;
  proposal: { opinions: …; changes: …; unaddressed: { segmentIds: number[]; startMs: number; speaker: string; text: string; reason: string }[] } | null; // 不含 dropped

  reviewVersionId: string | null; reviewVersionNumber: number | null;
  createdAt: string; updatedAt: string; confirmedAt: string | null;

```

`V19StudioModel` 新增两项：
- `audioReviews: V19AudioReviewSummary[]`：老孙看到这个案例的全部未放弃任务；其他人只看到 `GENERATED` 的。字段为 `{ id, baseVersionId, status, step, failReason, changeCount, reviewVersionId, reviewVersionNumber }`。
- `audioReviewAvailable: boolean`。

### 4.9 确认生成（`CONFIRM`）

在一个事务内完成：

1. 锁工作区，锁任务行。确认状态是 `PENDING_CONFIRM`，操作人是老孙，这一版还没有点评版。`selectedChangeIds` 必须非空，且都在 proposal 里。
2. 按 `targetKey` 合并选中的改动（细项合并成一个 `primaryDetails` 对象），生成 `V04Change[]`。`beforeValue` 取快照值。用 `applyV04ChangeSet` 套到快照上，并通过 `assertV04PayloadContract`。
3. 插入 `analysis_versions`：
   - `version_kind='AUDIO_REVIEW'`，`version_number` = 当前最大号 + 1；
   - `owner_user_id` 和 `owner_name_snapshot` 填老孙；
   - `base_version_id` / `base_version_number` 填被点评版本，`base_payload_json` 填快照，`base_captured_at` 取任务创建时间；
   - `audio_review_id` 填任务 id，`revision=1`，`payload_json` 为改后内容。
4. 每处改动写一条 `collaboration_revision_events`：`source_kind='AI_ACCEPTANCE_RESERVED'`（AI 改写、经人确认），`reason` 写「录音点评 意见 N」，`version_id` 填点评版。再写 `audit_logs`，动作为 `V19_AUDIO_REVIEW_GENERATED`。
5. 任务改为 `GENERATED`，写入 `review_version_id`、`selected_change_ids` 和 `confirmed_at`。
6. **不调用** `intakeIntoFinal`。

### 4.10 本地假实现

`AUDIO_REVIEW_PROVIDER=fake`（本机演示模式默认）用于本机预览和验收：

- 转写：两次推进后返回内置文字稿（demo 里那段「捉迷藏」点评）。
- 理解：按快照确定性地生成提案，覆盖总体意见（多处改动）、具体意见（单处）、选项字段、评价、细项、镜头字段和「没落到条目的话」。
- 键取自快照里真实的桥段和镜头 id；时长打折，让完整流程大约 10 秒走完。

## 五、点评版的读写

1. **保存**：PUT `/analysis/v19` 不改请求体。`saveV19VersionChanges` 先读 `basedOnVersionId` 指向的行：
   - 是 `AUDIO_REVIEW` 且操作人是它的 owner：写进这一行，走正常的修订事件和审计（`source_kind='HUMAN_DIRECT'`），不汇入集成版，返回 `finalIntake: { merged: 0, pending: 0 }`；
   - 否则走原逻辑：写进操作人的个人版本，没有就以 `basedOnVersionId` 指向的版本（可以是点评版）为底新建。
2. **GET 的 `canEdit`**：看点评版时，所有已登录成员都是 `true`，和普通版本一样，因为其他人的修改会转进自己的版本。
3. **前端编辑守卫**：`resolveV19EditGuard` 加一个分支。当前是点评版且看的人是它的 owner：直接编辑（PROCEED）。其他人：已有个人版本就切回自己的版本（SWITCH_TO_OWN）；没有就编辑，由服务端以点评版为底新建。
4. **评分**：点评版不显示评分组件（同集成版）。

## 六、集成版采纳

- `loadFinalTrace` 额外返回 `reviewCandidates`。对工作区里每个点评版，逐个 FIELD 键比较它当前内容和 `base_payload_json`，有差异的记为候选：`{ reviewVersionId, reviewVersionNumber, targetKey, targetLabel, value, updatedAt }`。键在集成版里不存在的（例如点评版里新插的镜头），或集成版当前值已经等于候选值的，都不列。
- 溯源视图里，每个条目在「未纳入」之后多一行「点评版 vN · 老孙录音点评 · 时间」，完整显示写法；老孙看到「采纳」按钮。这一行不计入「N 处未纳入」，「全部采纳」也不处理它。
- 采纳：POST `/analysis/v19/final` 新增 `{ action: "ADOPT_REVIEW", reviewVersionId, targetKeys: string[] }`。服务端重新计算候选，用 `applyFinalIntake(FIELD)` 写进集成版，并插入一条 `applied=true` 的汇入记录：`source='VERSION'`、`source_version_id` 填点评版、`source_version_number` 填其编号。这样溯源里显示「当前采用 · vN 老孙录音点评」。同样只有老孙能调。
- 集成版处于定稿态时也允许采纳（采纳本来就是老孙主动做的）。

## 七、前端（以 demo 为准，类名、配色、共用 toast、抽屉和弹层都复用站内现有组件与写法）

1. `V19AudioReviewEntry`：页头入口，五种形态：上传按钮、处理中胶囊（转圈 + 当前步骤 + 进度气泡）、失败胶囊（原因 + 重试／重新上传）、待确认胶囊（主色底）、「查看点评版 vN」。
2. `V19AudioReviewUploadDialog`：选文件后立即上传，XHR 显示进度。上传完自动调 `UPLOADED` 并关闭弹层，toast「录音已上传，正在处理……」。
3. `V19AudioReviewDrawer`：确认面板（demo 右侧抽屉），包含录音条、意见卡、改动勾选、没落到条目的话、文字稿。底部按钮：放弃这次点评／重新上传／生成点评版。生成后切到点评版并打开比较，toast「点评版 vN 已生成……」。
4. `V19AudioReviewCard`：点评版顶部的录音卡，用真实的 `<audio>`。点时间点会跳转并播放，文字稿随播放高亮当前句。
5. 被点评版本上的提示条（2-10）、版本菜单的点评版行和标记、页头版本胶囊的点评版写法。
6. `V19StudioDocument` 新增可选属性 `reviewBasis: Map<targetKey | "path.primaryDetails.<sub>", { numbers: number[]; tip: string }>`，比较开启时在差异标记旁画「依据 意见 N」。
7. 轮询：页面可见且有在途任务时，每 4 秒 GET 一次；切到后台暂停；任务状态变化时刷新 `audioReviews`。到 `PENDING_CONFIRM` 时只 toast 一次。
8. 集成版溯源里的点评版候选行与「采纳」按钮（第六节）。
9. 深浅两套主题只用 `--v04-*` 变量；手机宽度下抽屉占满全宽、没有横向溢出。

## 十、验收清单

1. 迁移可重复执行；执行后个人版本仍然每人唯一（重复插入被挡下）；点评版可以和老孙的个人版本共存；同一基版第二个点评版被挡下。
2. 第 3.3 节表里每一处都有测试：点评版不进集成版回放、不计入案例卡版本数、不能评分、不会成为「我的版本」或默认版本、Agent 接口 `latest` 不返回它。
3. 签名：TC3 签名有固定向量测试（对照腾讯云文档示例）。转写结果解析和错误码映射都有测试。
4. 提案校验：非法键、非法选项、时间码改动、空值、重复键、细项合并、主导类型切换各有测试。
5. 流水线：租约互斥、时间不够不开模型、失败两次转 FAILED、RETRY 从失败步继续、ABANDON 后能重新上传、CONFIRM 幂等（重复调用不产生第二个版本）。
6. 权限：非老孙调用任何写接口回 403；非老孙 GET 非 `GENERATED` 任务回 404；路由检查顺序有源码测试。
7. 本机 fake 全流程走通：老孙上传 → 处理 → 确认（取消一处）→ 生成点评版 → 比较与依据标记 → 老孙直接改点评版 → 其他身份在点评版上编辑转进自己的版本 → 集成版溯源里采纳一处并显示来源。深浅主题和手机宽度都要截图。
8. `npm test`、`npm run lint`、`npm run build` 全绿。

## 十一、本期不做

- 被点评人一键把点评版的改动并进自己的版本（对照着自己改）。
- 一段录音点评多份作业（自动切分）。
- 点评版里新插入的镜头、桥段被采纳进集成版。
- 录音在线剪辑、说话人改名。
