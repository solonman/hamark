# 单用户单片分析入口优化设计

## 目标

让“写下我的分析”符合一人一片只能有一份分析的产品规则：用户没写过时进入创建流程；已有草稿或已提交内容时，入口改为继续编辑同一份分析，避免重复创建的心理预期。

## 保持不变

- 每个用户在同一个视频下仍只有一条 `annotations` 草稿记录，读取条件保持 `video_id + author_email + deleted_at IS NULL`。
- 公开分析列表仍按每位作者最新提交版本展示，不允许同一作者在列表里出现多篇。
- 作业填写页、自动保存、提交校验、评分入口和视频播放逻辑不改变。
- 已提交后再次进入编辑页，仍编辑同一份底稿；后续重新提交会产生新的公开快照版本。

## 方案

视频详情接口在返回视频和公开分析列表时，同时查询当前登录用户在该视频下的 `annotations` 状态。返回一个轻量字段，例如 `myAnalysis`，包含是否存在、状态和修订号。它只描述当前用户自己的分析，不影响其他人的公开分析数据。

视频详情页根据 `myAnalysis` 切换主入口文案：

- 没有记录：显示“写下我的分析 ↗”。
- 有草稿：显示“继续编辑我的分析 ↗”。
- 已提交：显示“查看并编辑我的分析 ↗”。

这些入口都指向既有 `/videos/[id]/practice`，由现有作业页加载同一份 `annotations` 记录。空状态里的“开始逆向”继续保留，但语义同样是进入我的唯一分析。

## 数据与边界

后端以服务端登录身份判断 `myAnalysis`，前端不自行推断当前用户是否出现在公开列表里，避免同名用户或公开列表缺失造成错误状态。

如果用户已有已提交分析但公开快照读取失败，入口仍根据 `annotations.status` 显示“查看并编辑我的分析”，因为入口状态依赖自己的底稿，不依赖公开列表渲染。

## 验证

- 测试视频详情接口会返回当前用户的分析状态。
- 测试未写、草稿、已提交三种状态下的按钮文案。
- 运行相关测试，必要时运行 lint 或构建确认类型和页面编译通过。
