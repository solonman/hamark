## 一、目标与真实场景

博加每月开一次客户服务复盘会（13:30–18:00）。各部门各讲一个真实案例，老孙通过追问、分析和点评带教，**每讲完一个案例停一次录音，最后老孙的整场总结单独录一段**。

网站要做三件事：

1. **会前**：各部门在网站上用表单把案例的来龙去脉填好，包括初始需求、每一回合「我们交了什么 → 客户怎么反馈 → 我们怎么应对」、结果。现场可以直接打开案例页投屏讲。
2. **会后**：任何人把每段录音传到对应案例上，整场总结传到当月；系统转写成文字。
3. **整理**：老孙在当月页面点「生成」。AI 先逐个案例提炼，再汇总出两份成果：**① 教学纪要**（面向中层）、**② 方法提取记录**（面向公司长期积累，内容全部是「方法候选」）。老孙审阅、修改、确认后发布，全员可见。

每一条判断都能追回出处：哪个案例、哪一回合、录音第几分几秒老孙的原话。

## 二、已定的产品口径（2026-10-14 项目负责人确认）

1. 页签名「**客户需求复盘库**」，作为第四个库，和视频库、报告库、公共视觉库并列。
2. **没有协调人**。案例和现有三个库一样，由用户自己上传，并且用**表单**填，不是先做 PPT 再上传。
3. 场次不单独建。案例**按复盘月份自动归组**；教学纪要和方法提取记录挂在月份上。每月有几个案例不写死。
4. 录音**按案例分段录，再加一段整场总结**，会后上传文件（手机或录音笔）。**任何人都能传录音**。本期不对接腾讯会议，也不做网页录音。
5. **全员可见**：案例、录音、文字稿，以及发布后的纪要和方法记录。
6. 交付稿**可以关联**视频库、报告库里已有的作品，不用重复上传。
7. AI 产出**由老孙确认**后才发布。

## 三、对 AI 的硬约束（来自需求文档，写进提示词，并由校验兜底）

1. **只提取录音里有依据的东西**。每一条方法候选、核心认识、改进事项都必须引用至少一句录音原话（片段编号）；引不出来的丢掉。原话由服务端按片段编号取出展示，**不让模型自己写引文**，从根上杜绝编造。
2. **不替老孙发明理论**。不得把分析套进任何现成框架，**尤其不得强行整理成黄金圈（Why／What／How）**；老孙原话里用了这类说法，可以照实记录。
3. **区分三类东西**，每条方法候选必须标出一类：
   - `METHOD` 相对稳定的思维方法；
   - `INTUITION` 基于经验的专业直觉。只记老孙的判断和他实际说出的理由，**不替他补全逻辑**；
   - `SITUATIONAL` 针对特定情境的判断。必须写明是什么情境（客户性格、合作历史、现场气氛……）。
4. **只是候选**。本期产出的方法全部叫「方法候选」，界面和数据上都没有「正式方法」。升为正式方法要在二期由老孙审定（第十三节）。
5. **出现次数不等于重要性**。不按频次排序、不打重要度分；只出现一次但有分量的判断照样保留。
6. **不机械凑数**。不要求每个案例出三条，核心认识和改进事项按实际讨论来，可以很少。
7. 改进事项**只保留能执行的**：写清在什么时候、由谁、做什么。
8. 录音里汇报人和其他同事的话只用来理解上下文。**方法候选只从老孙的话里提**；纪要里的「关键争议」可以引用各方。

## 四、案例

### 4.1 命名与入口

| 项 | 取值 |
|---|---|
| 页签名 | 客户需求复盘库 |
| 页签参数 | `?library=RETRO` |
| 案例详情 | `/retro/[id]` |
| 月份页 | `/retro/months/[YYYY-MM]` |
| 接口前缀 | `/api/retro-cases`、`/api/retro-months` |
| 开关 | `RETRO_LIBRARY_ENABLED`，默认关；关闭时页签在、显示「建设中」，接口一律 404（同公共视觉库） |

和公共视觉一样，**不登记专业域**，不挂 V0.4 契约，不建版本链（理由同 docs/22 2.3）。

### 4.2 表单字段

新建分两步，详见 10.4：先在对话框里填**基本信息**（五项）并创建，然后在案例页上**原位编辑**：点一下就能填**任务与最初需求**、逐个添加**回合**，失焦自动保存，没有编辑模式，也没有保存按钮（2026-10-19 项目负责人改：需求不在新建对话框里填）。

**基本信息**

| 字段 | 控件 | 约束 |
|---|---|---|
| 复盘月份 | 下拉：上月／本月／下月 | 必填，默认本月；存 `YYYY-MM`；编辑时可以改成任意过去的月份 |
| 部门 | 单行框，下拉提示里列出已有的部门名 | 必填，1–30 字 |
| 客户 | 单行 | 必填，1–60 字 |
| 案例标题 | 单行 | 必填，1–80 字，提示「一句话说清这件事，如：年货节主视觉三次被否」 |
| 客户服务场景 | 逗号分隔的标签 | 选填，0–8 个，每个 ≤20 字；归一与去重规则同 docs/22 3.3.1。提示里举例：提案、改稿、客户情绪、需求变更、比稿、结案 |

**任务与最初需求**（在案例页原位编辑）

| 字段 | 约束 |
|---|---|
| 任务与最初需求 | **选填**，≤5000 字。空着时，有编辑权的人看到灰色占位「点击填写任务与最初需求：客户最开始要什么，当时的背景和约束」，不拦截；其他人看到灰字「还没有填写任务与最初需求」 |
| 需求凭证（附件） | 选填，客户需求的原始凭证：截图、客户语音或通话录音、brief 文档等，≤12 个，见 4.3 |

**回合**（0–20 个，按 `position` 排列）

| 字段 | 约束 |
|---|---|
| 回合标题 | 1–40 字，默认「第 N 版」，可以改成「比稿」「电话沟通」等 |
| 时间 | 选填，原文保存，如「9 月中」「2026-09-18」 |
| 我们交了什么 | 选填，≤5000 字。提示「这一版的核心想法、和上一版相比改了什么」 |
| 客户怎么反馈 | 选填，≤5000 字。提示「尽量用客户原话」 |
| 我们怎么应对 | 选填，≤5000 字 |
| 附件 | 图片、视频、音频、文档，每回合 ≤12 个，见 4.3 |
| 关联作品 | 视频库、报告库、公共视觉库里的条目，每回合 ≤6 个，见 4.4 |

三段文字都空着的回合，在 AI 输入里只出现标题，不报错。

需求模块和每个回合都写同一句提示：「AI 只读这里的文字，看不到附件：关键内容请用文字写清楚」。

**收尾**

| 字段 | 约束 |
|---|---|
| 结果 | 选填，≤3000 字。如「客户接受第三版，项目延期两周」「仍在进行」 |
| 关键转折 | 选填，≤3000 字。上传人自己认为的转折点 |
| 希望讨论的问题 | 选填，≤2000 字。想请老孙和大家一起看的问题（工程建议的字段，见 14-2） |

### 4.3 附件

附件挂在两个地方：「任务与最初需求」模块（需求凭证）和每个回合。两处规则完全相同（2026-10-19 统一）：

- **图片**（JPEG／PNG／WebP／HEIC）：派生图链路照抄公共视觉，数据万象出 480w 和 1600w 两档，本机走脚本，20MB 以上不出预览。
- **视频**：不转码，浏览器截帧作封面，站内播放走 `stream` 路由。
- **音频**（客户语音、通话录音等，统称「客户录音」，格式同 5.1）：**传完自动转写**（2026-10-19 项目负责人定：不转写 AI 的上下文不全）。转写走和点评录音同一条链路（5.2），状态有 转写中／就绪／转写失败（可重试）。格上显示文件名、时长和状态；点开是播放条，下面展开文字稿（说话人 1、2…，可点时间点跳转，播放时高亮当前句），全员可见。客户录音和「点评录音」是两回事：它进 AI 输入作为上下文，但**不能作为方法候选的依据**（6.4）。
- **文档**：PDF 点开时签 GET，在新标签页由浏览器打开；Word／Excel／PPT（doc/docx/xls/xlsx/ppt/pptx/key）点开是下载（`Content-Disposition: attachment`），不做预览。想在网页里逐页看 PPT 的，仍然可以先传到报告库，再在回合里关联。
- 其它类型拒收，提示支持哪几类。
- 上传方式照公共视觉：建附件行 → 用到哪个签哪个（600 秒）→ 同时传 3 个 → complete 用 `head()` 核对。部分失败时列出没传上的，可以重传或去掉。
- 编辑时移除附件是**真删**，对话框当场提示，文案同 docs/22 6.4（决定 #20 的做法）。

### 4.4 关联已有作品

- 回合里点「关联作品」，打开选择框：三个页签（视频库／报告库／公共视觉库），带搜索，可以多选。数据直接用三个库现有的列表接口，不新开查询。
- 展示成小卡片：缩略图、库名、标题，点进去到原作品页。原作品被删除后显示「原作品已删除」，关联本身保留。
- 进 AI 输入的只有：库名、标题、品牌或客户、标签、一句话摘要。**不展开视频拆解的全文**，那样一个案例的输入会膨胀到失控；回合文字才是主要输入。

### 4.5 编辑权与删除

| 动作 | 谁能做 |
|---|---|
| 新建案例 | 任何已登录成员 |
| 改基本信息、回合、附件、关联、收尾 | 原上传者；系统管理员 |
| 给案例传录音、给月份传总结录音 | **任何已登录成员**（二-4） |
| 移除一段录音 | 这段录音的上传者、案例上传者、系统管理员（软删除，文件不删） |
| 删除案例 | 原上传者与系统管理员。移入回收站，可以恢复；文件不清理；确认框文案与三个库相同 |
| 查看 | 全员 |

没有权限的人看不到按钮，接口返回 403。所有写操作走 `requireSameOriginMutation`。「老孙」这个身份只赋予生成、审阅、发布的权限（第六节）。他能不能改别人的案例，取决于他是不是系统管理员，不另开例外。

## 五、录音

### 5.1 挂在哪里

界面上统一叫「**点评录音**」（2026-10-19 项目负责人定），和附件里的客户语音区分开。

- **案例录音**：挂在案例上，最多 3 段（录音中途断过、换过设备时用），按段号顺序拼成一份文字稿。
- **整场总结**：挂在月份上（`case_id` 为空），同样最多 3 段。
- 格式与大小照 docs/25 4.2：`audio/*` 或 m4a／mp3／wav／aac／flac／ogg／amr／wma／3gp／mp4，单段不超过 500MB。直接复用 `validateAudioReviewFile` 和 `putAudioReviewFile`。

### 5.2 处理：只转写

```
UPLOADING ──UPLOADED──▶ TRANSCRIBING ──▶ READY
    │                        └──失败──▶ FAILED ──RETRY──▶ TRANSCRIBING
    └──────────────移除──────────────▶ REMOVED（任何状态都能移除）
```

- 点评录音和附件里的客户录音（4.3）都走这条转写链路。转写复用 `lib/audio-review/tencent-asr.ts`，参数照 docs/25 4.4（`16k_zh_en_2.0`、说话人分离）。热词取：客户名、部门名、案例标题里的词、场景标签、回合标题、「老孙」、上传人姓名，去重后最多 128 个。
- 推进方式照 docs/25 4.3：上传完成和每次 GET 都用 `after()` 推进，带租约；案例页可见时每 4 秒拉一次。
- **转写完就全员可见**：录音条和文字稿立即出现在案例页上。说话人此时只显示「说话人 1、2…」；当月纪要发布后，换成 AI 认出的称呼（老孙／汇报人／其他同事），见 6.4。
- 录音和文字稿**没有 AI 解读**，所以不需要等老孙确认。
- 发布后才新传的录音，说话人仍然显示「说话人 N」，因为 AI 还没认过；等下一次发布时，再换成认出的称呼。

### 5.3 换录音

- 移除一段后可以重新上传。移除是软删除：行和对象都保留，已发布成果里引用它的片段仍然能打开、能播放。
- 当月纪要发布后，如果录音又有变动（新增、移除），月份页给老孙提示「发布后有 N 段录音变动，可以重新生成」。不自动重算。

## 六、月度整理（AI 流水线）

### 6.1 谁、什么时候

- **只有老孙**能在月份页点「生成本月纪要与方法记录」。
- 前提条件：当月至少有一个案例的点评录音 `READY`，并且没有点评录音或客户录音还在 `UPLOADING`／`TRANSCRIBING`。不满足时按钮灰掉，旁边写原因。前提条件清单里分开列点评录音和客户录音，例如「客户录音 3 段 · 已转写 2 · 转写中 1」。
- 有客户录音转写失败时，确认框里加一句「有 N 段客户录音转写失败，它们不会进入提炼」。
- 有案例没有录音时，先弹确认框：「有 N 个案例没有录音：它们会列在纪要的案例清单里，但不参与提炼。继续生成？」
- 没有整场总结录音也可以生成，确认框里一并提一句。

### 6.2 状态

```
QUEUED ─▶ EXTRACTING(i/N) ─▶ SUMMARIZING ─▶ DISTILLING ─▶ PENDING_REVIEW ──发布──▶ PUBLISHED
   │            │                 │              │               │
   └────────────┴─────────────────┴──────────────┴───────────────┴──放弃──▶ ABANDONED
                └──失败──▶ FAILED(step) ──RETRY──▶ 回到失败的那一步
```

- 同一个月同时只能有一个未结束的任务（部分唯一索引）。`PUBLISHED`、`ABANDONED` 是终态。
- 已经发布过的月份可以再次生成，产生新草稿；再发布就是 v2，v1 原样保留（6.6）。
- 老孙在 `PENDING_REVIEW` 时点「重新生成」，等于放弃当前草稿再开一个新任务，草稿上的修改会丢，先确认。

### 6.3 三步

**为什么要拆**：一个月 4.5 小时录音，转写约 7–8 万字。单次模型调用受两个限制：本仓库 Vercel 函数 300 秒（模型调用超时 240 秒），以及输出上限 32k token。一次调用写不完两份成果，所以拆成每次只做一件事。

| 步骤 | 每次调用的输入 | 输出 | 次数 |
|---|---|---|---|
| ① 逐案提炼 `EXTRACTING` | 一个案例的表单文字（含回合、关联作品摘要）+ 这个案例的客户录音文字稿（标明挂在需求还是第几回合）+ 这个案例的全部点评录音片段 | 这个案例的回顾、说话人认定、方法候选（6.4） | 每个有录音的案例一次 |
| ② 汇总纪要 `SUMMARIZING` | 全部案例的提炼结果 + 整场总结的文字稿 | 教学纪要（6.5） | 一次 |
| ③ 汇总方法 `DISTILLING` | 全部案例的方法候选 + 整场总结的文字稿 | 方法提取记录（6.5） | 一次 |

- 每次推进**只做一次模型调用**；剩余时间不足 245 秒就不开始，留给下一次推进（同 docs/25 4.3）。
- 每次调用失败自动再试一次，第二次改用 `reasoning_effort: "low"`；仍然失败就转 `FAILED(step)`。①失败时记下是第几个案例，重试从这个案例接着做。
- **缓存**：①的结果按「案例输入哈希」存。重新生成时，输入没变的案例直接复用，不再调模型。
- **接力推进**：6 个案例加两步汇总，约 8 次调用、10–15 分钟。老孙不会一直开着页面，所以每推进完一步，就在 `after()` 里向自己发一个内部推进请求，接着跑下一步。内部请求带 HMAC 令牌，内容是任务 id 加步骤序号，密钥 `RETRO_RELAY_SECRET`，用一次作废。
- 兜底：月份页 GET 照样会推进。所以接力链万一断了，老孙打开页面也能接上。仓库目前没有 Vercel Cron，不依赖它。
- 模型、提示词版本、输入哈希、用量逐次记进任务行（docs/03 3.3）。

### 6.4 逐案提炼的输出（模型返回，服务端校验后存）

```json
{
  "speakers": { "founder": "S0", "labels": { "S1": "汇报人", "S2": "其他同事" } },
  "review": {
    "process":       "业务问题及其发展过程（叙述）",
    "disputes":      [ { "text": "…", "segmentIds": [12, 13] } ],
    "founderPoints": [ { "text": "老孙指出的问题", "segmentIds": [20], "roundIds": ["rnd_2"] } ],
    "suggestions":   [ { "text": "最终提出的改进建议", "segmentIds": [41] } ]
  },
  "insights": [ { "text": "可能进入核心认识的点", "segmentIds": [33] } ],
  "actions":  [ { "text": "可执行的改进事项", "segmentIds": [44] } ],
  "methods": [
    {
      "dimension": "ENTRY",
      "kind": "METHOD",
      "title": "先问客户为什么提这个要求",
      "description": "老孙怎么做、为什么（只写录音里有的）",
      "situation": "",
      "transfer": "TRANSFERABLE",
      "transferNote": "可用于任何客户提出具体修改意见的场合",
      "segmentIds": [20, 22],
      "roundIds": ["rnd_2"]
    }
  ],
  "corrections": [ { "segmentId": 9, "from": "…", "to": "…" } ]
}
```

- `dimension`（分析维度，对应需求文档的表格）：`ENTRY` 问题切入、`INFO` 信息判断、`PATH` 分析路径、`VALUE` 价值判断、`SOLUTION` 解决思路、`INTERACTION` 互动方法。需求文档的第七项「方法迁移」不单列为维度，而是每条候选都要回答的属性：`transfer` 取 `TRANSFERABLE` 可迁移、`CASE_ONLY` 只适用本案、`UNSURE` 说不准，`transferNote` 写理由。
- `kind`：`METHOD`／`INTUITION`／`SITUATIONAL`（三-3）。`SITUATIONAL` 的 `situation` 必填。
- `roundIds` 指向案例的回合，用来落实「你看第二版这里」。

**校验与归一**（`lib/retro/extraction.ts`，纯函数，重点测试）：

- `segmentIds` 必须存在于这个案例的文字稿里；`roundIds` 必须是这个案例未删除的回合；不存在的引用剔除。
- 客户录音的片段用 `c<assetId>:<segmentId>` 的形式引用，和点评录音片段区分。它们**只能出现在 `review.process` 和 `review.disputes` 里**（作为「客户原话」的出处）；出现在方法候选、核心认识、改进事项、老孙指出的问题、改进建议里的，一律剔除。
- 客户录音进提示词有长度上限：每个案例合计 3 万字，超出的按时间截断并在输入里注明「以下省略」，避免一小时的通话录音把输入撑爆。
- 方法候选的 `segmentIds` 里**至少有一句是 `speakers.founder` 说的**，否则整条丢弃。丢弃原因记进 `dropped`，只用于排查，不展示。
- `insights`、`actions`、`founderPoints`、`suggestions` 剔除无效引用后，一句都不剩就丢弃。`disputes` 可以引用任何人。
- 枚举值不合法、标题为空、`SITUATIONAL` 没写情境，都丢弃。
- 文字去首尾空白，长度上限：标题 40 字、其他 600 字。
- 各项不设最少条数（三-6）。全部被丢光的案例，在纪要里写「这个案例没有提炼出有依据的内容」，不算失败。

### 6.5 两份成果的结构

**教学纪要** `minutes`

```ts
{
  cases: { caseId; process: string; disputes: Item[]; founderPoints: Item[]; suggestions: Item[] }[];  // 直接取自①，模型不重写
  insights: Item[];   // 本次培训的核心认识：跨案例归纳，不按案例凑数
  actions: Item[];    // 可以进入实际工作的改进事项
}
type Item = { id: string; text: string; sources: Source[]; origin: "AI" | "MANUAL"; edited: boolean };
type Source =
  | { kind: "REVIEW"; recordingId: string; segmentIds: number[]; caseId: string | null; roundIds?: string[] }   // 点评录音
  | { kind: "CLIENT"; assetId: string; segmentIds: number[]; caseId: string; roundId: string | null };         // 客户录音，只用于经过和关键争议
```

**方法提取记录** `methods`

```ts
{
  candidates: {
    id; number; dimension; kind; title; description; situation; transfer; transferNote;
    sources: Source[];            // 可以跨多个案例；引用的片段原文由服务端取
    origin: "AI" | "MANUAL"; edited: boolean;
  }[];
  observations: Item[];           // 本月值得注意的：同一思路在不同情境下的差异、看似矛盾的判断
}
```

- ③可以把不同案例里的同一思路合成一条，`sources` 取并集；**但不同情境下做法不同的，要分开列，或者写进 `observations`**，不能强行合并（需求文档「这些差异也值得保留」）。
- 汇总步骤的输出同样要校验：`sources` 只能引用①里已有的引用，或者整场总结里真实存在的片段。

### 6.6 审阅、修改与发布

- `PENDING_REVIEW` 时，月份页的「教学纪要」「方法提取记录」两个页签显示草稿。页首写「草稿 · 只有你看得到」，只有老孙能看。
- 草稿各部分能做什么：
  - 案例回顾的「经过」只能改，不能删；
  - 争议、老孙指出的问题、改进建议能改、能删，不能补；
  - 核心认识、改进事项、方法候选、本月观察，能改、能删、能补；
  - 删除不二次确认，弹 toast 告知。
- 老孙可以：改任何一条的文字（`edited=true`）；删掉一条；在核心认识、改进事项、方法候选、本月观察里**手动加一条**（`origin=MANUAL`，标「老孙补充」，可以不带出处）；改方法候选的维度、类别、迁移性。保存方式同工作台，失焦自动保存。
- 「发布」：一个事务内写入 `retro_month_publications`（v1、v2…），完整保存两份成果和它们引用的片段原文快照，并把方法候选逐条写进 `retro_method_candidates`，供二期使用。任务转 `PUBLISHED`。写一条 `audit_logs`，动作为 `RETRO_MONTH_PUBLISHED`。
- 发布后全员可见。旧版本留在「历史版本」下拉里，可以切换查看，**不能改**。发布之后发现错字怎么办：重新生成会丢掉所有修改，代价太大，所以给老孙一个「修订已发布内容」：基于当前发布版复制出新草稿（不调模型），改完再发布成 v(N+1)。
- 发布后，各案例页底部出现「在本月纪要里」：这个案例的回顾，以及引用了这个案例的方法候选。

### 6.7 出处的展示

- 每一条带出处的内容后面跟一个或几个小标记，形如「案例 2 · 12:40」「总结 · 03:15」。
  - 「案例 N」是当月案例按创建先后的序号，生成时冻结进 `input_snapshot_json`。案例后来被删除，序号照样占着，已发布纪要里的标记不会错位。卡片上的 `CASE` 编号另算：照其它库，按全库倒序编号。
  - 案例有多段录音时，标记写成「案例 1 · 第 2 段 05:10」；只有一段时不写段号。
- 点标记弹出小浮层：列出被引用的句子（说话人、时间点、原文），底部是「去听原声」，跳到案例页并从这个时间点开始播放（`/retro/[id]?t=760#recording`）。
- 引用了回合的，再加一个「第二版」标记，点击跳到案例页的那一回合。

### 6.8 提示词

- `lib/retro/prompt.ts`，三个提示词版本常量：`RETRO_EXTRACT_PROMPT_VERSION`、`RETRO_MINUTES_PROMPT_VERSION`、`RETRO_METHODS_PROMPT_VERSION`。
- system 里写死第三节的八条约束，并附上维度、类别、迁移性的中文释义和反例，例如：「老孙说『先别急着改，先问清楚他为什么要改』→ ENTRY／METHOD」；「老孙说『这种客户你得先让他把火发完』→ INTERACTION／SITUATIONAL，情境：客户当场情绪激动」。
- **维度和类别的释义由工程起草，请老孙校订**，做法同 docs/25 的字段说明。
- 质量核对脚本 `web/scripts/retro-prompt-check.ts`：读本机录音的转写结果，跑一遍三步，输出到终端，用来调提示词。真实调用要先经项目负责人同意（付费）。

## 九、接口

鉴权一律 `requireApiUser`，写操作加 `requireSameOriginMutation`，检查顺序为同源 → 登录 → 业务。凡是会调外部服务的路由都写 `maxDuration = 300`。

| 方法与路径 | 作用 |
|---|---|
| `GET /api/retro-cases` | 全量列表：卡片字段、回合数、录音概况（段数、总时长、是否都 READY）、`canManage` |
| `POST /api/retro-cases` | 新建，传基本信息，返回 `caseId` |
| `GET /api/retro-cases/[id]` | 详情：基本信息、回合（含附件签名缩略图、关联作品摘要）、收尾、录音（含文字稿）、当月已发布成果里与本案相关的部分、`viewerCapabilities` |
| `PATCH /api/retro-cases/[id]` | 改基本信息、收尾，带 `revision` 乐观锁，对不上回 409 |
| `POST /api/retro-cases/[id]/rounds` ／ `PATCH …/rounds/[roundId]` ／ `DELETE …/rounds/[roundId]` | 回合的增、改、软删；`PATCH /api/retro-cases/[id]/round-order` 整体重写顺序 |
| `POST /api/retro-cases/[id]/assets`（body 带 `roundId \| null`）、`…/assets/[assetId]/upload-url`、`POST /api/retro-cases/[id]/assets/complete`、`DELETE …/assets/[assetId]` | 附件（需求凭证与回合附件共用），形状照公共视觉 |
| `GET …/assets/[assetId]/original` ／ `stream` | 查看 PDF 或原图、下载 Office 文档、播放视频或音频，302 到新签的地址 |
| `GET /api/retro-cases/[id]/assets/[assetId]/transcript` ／ `POST …/transcript`（`{ action: "RETRY" }`） | 客户录音的转写状态与文字稿；GET 时未到终态用 `after()` 推进，同 5.2 |
| `PUT …/rounds/[roundId]/links` | 整体写回这一回合的关联作品 |
| `POST /api/retro-cases/[id]/trash` ／ `restore` | 删除、恢复 |
| `POST /api/retro-recordings` | `{ monthKey, caseId \| null, fileName, contentType, sizeBytes }` → `{ recording, uploadUrl }`；段号自动取下一个，满 3 段回 409 |
| `GET /api/retro-recordings/[id]` | 状态与文字稿；未到终态时用 `after()` 推进 |
| `POST /api/retro-recordings/[id]` | `{ action: "UPLOADED" \| "RETRY" \| "REMOVE" }` |
| `GET /api/retro-recordings/[id]/audio` | 307 到预签名 GET（3 小时），供 `<audio src>` 使用 |
| `GET /api/retro-months/[month]` | 月份页：案例清单与录音概况、总结录音、最新发布版（及历史版本号列表）、`job`（只有老孙能看到 `PENDING_REVIEW` 的草稿内容，其他人只看到「整理中」）；有在途任务时用 `after()` 推进 |
| `GET /api/retro-months/[month]/publications/[n]` | 历史版本 |
| `POST /api/retro-months/[month]/jobs` | 老孙发起生成：`{ mode: "GENERATE" \| "REVISE_PUBLISHED" }` |
| `POST /api/retro-months/[month]/jobs/[jobId]` | 老孙操作：`{ action: "RETRY" \| "ABANDON" \| "PUBLISH" }` |
| `PATCH /api/retro-months/[month]/jobs/[jobId]/draft` | 老孙改草稿：`{ section, itemId?, op: "UPDATE" \| "DELETE" \| "ADD", value }`，带 `revision` |
| `POST /api/retro-months/[month]/jobs/[jobId]/advance` | 内部接力（6.3），只认 HMAC 令牌，不认登录态；令牌无效回 404 |

非老孙调用生成、审阅、发布类接口一律 403；非老孙读草稿内容拿到的是空。路由检查顺序用读源码的方式测试，同仓库惯例。

### 10.3 案例页 `/retro/[id]`

- **顶栏**：站标 ｜ 案例标题（截断）+「客户需求复盘库」返回链接 ｜ 外观、用户。
- **detailHero**：面包屑「客户需求复盘库 / 2026 年 10 月」，月份可点；眉题「部门 · 客户 · 2026 年 10 月复盘」；标题；场景标签；动作行：上传者和管理员看到「编辑基本信息」「删除案例」。「编辑基本信息」打开新建对话框的同一个外壳（眉题 `EDIT`，五项预填，按钮「保存」）。hero 里**不放**上传点评录音的按钮，入口只在点评录音模块和卡片上。

  1. 「任务与最初需求」（`readingModule`）：文字加需求凭证附件格。
  2. **过程时间线**：每一回合一张卡，左侧竖线连起来，卡头是「第 2 版 · 9 月中」。卡内三段依次是「我们交了什么」「客户怎么反馈」「我们怎么应对」，空的段不渲染。下面是附件格（图片缩略图、视频封面带 ▶、音频格带时长和转写状态、点开有文字稿，文档格是类型图标加文件名）和关联作品小卡。
  3. 「结果」「关键转折」「希望讨论的问题」：有内容才渲染。
  4. **点评录音**（`id="recording"`）：没有录音时，收成一行窄条「点评录音 · 开完复盘会后，把这个案例的点评录音传到这里」，右侧是「上传」，任何人可见可点；这样填案例时它不占地方，也不抢注意力（2026-10-19 项目负责人：填案例时还没有点评）。只要有录音（包括上传中、转写中、失败），就展开成完整模块：有录音时，是录音条（多段时有「第 1 段／第 2 段」切换）和完整文字稿。处理中、失败用胶囊显示，失败时可以重试或移除重传。地址带 `?t=秒数` 时，自动滚到这里，从该时间点播放，并高亮当前句。
  5. **在本月纪要里**：只在**这个案例包含在已发布版本里**时出现（按发布时冻结的案例清单判断）；发布之后才新建的案例不出现。内容是这个案例的回顾（经过、争议、老孙指出的问题、改进建议），加上引用了这个案例的方法候选，每条都带出处标记（6.7）。底部是「看本月完整纪要 →」。
- **原位编辑**（同视频工作台，复用 `V19EditableValue`；2026-10-19 去掉了「编辑／完成」模式）：
  - 阅读态就是正文。有编辑权的人点一下字段（或按 Enter／Space）变成输入框，失焦或回车提交，字段旁短暂显示「已保存」。没有全局编辑模式，也没有保存按钮。
  - 可原位编辑的字段：任务与最初需求、回合的标题／时间／三段文字、结果、关键转折、希望讨论的问题。空字段对有编辑权的人显示灰色占位「点击填写…」；对其他人不渲染。
  - 结构控件常驻，但样式克制（小号、muted 色，悬停才高亮），不能让页面看起来像表单：回合卡右上角的 ↑ ↓ 和删除、时间线末尾的「＋ 添加一回合」、附件格的「＋ 附件」和每格的 ×、「关联作品」。

## 十三、分期与本期不做

**一期（本文）**：案例表单、附件与关联、分段录音与转写、月度三步整理、老孙审阅与发布、出处回溯。

**二期：方法库**（需要等一期积累几个月的数据，到时另写规格）
- 库里加「方法」视图：老孙对每条方法候选执行「升为正式方法」「并入已有方法」「驳回」「暂留」；正式方法挂着它的全部出处（跨月、跨案例）。
- 新一个月提取出候选时，标出「疑似与已有方法 X 相同」，方便合并。
- 按方法检索案例。
- 外部 Agent 只读接口加复盘库。

**三期：季度跨月比较**：攒满三个月后，AI 比较各月的候选，找出反复出现的、稳定的判断标准，只在特殊场景出现的，互相矛盾的，以及新出现的认识。**不以频次论重要性**。老孙只审要提升的关键结论。

**明确不做**：
- 对接腾讯会议、网页录音（二-4）；
- AI 读附件内容（图片识别、PDF 文字）；
- 中层分析表现的跨月比较（需求文档末尾提到的培训效果评价）；
- 案例的版本历史（改了就是改了，同公共视觉）；
- 评论、评分、收藏。

## 十四、工程先定的几项（2026-10-19 已确认）

1. **不做收藏和按周显示**。另外三个库的收藏服务于每周评选或留档；复盘案例按月开会，不参与评选。要做的话，照公共视觉加不限数量的收藏，成本很低。
2. **加了「希望讨论的问题」这个选填字段**。需求文档里没有，但会前让汇报人写下想讨论什么，老孙浏览时最有用，AI 也能借它理解讨论的走向。
3. **部门用自由填写，带已有部门名的下拉提示**，不设固定清单。如果博加的部门名是固定的几个，给我清单，我改成下拉框。
