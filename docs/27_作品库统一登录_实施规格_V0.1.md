# 27 · 作品库（AdVault）统一登录｜实施规格 V0.1

- 日期：2026-11-03
- 状态：**已冻结**（2026-11-03）。第二节、第三节均由项目负责人确认：第三节第 1 项按负责人意见改为「顶栏直接跳转、新标签页打开」，第 2–4 项照工程建议。
- 目标：把内部作品评比网站 AdVault（https://advault.boga.plus）挂成 hamark（https://hamark.boga.plus）的第五个库「作品库」，**全员只在 hamark 扫一次企业微信码**，进 AdVault 不再登录。
- 涉及两个仓库：本仓库 `web/`，以及 `solonman/AdVault`（本机 `~/Desktop/AdVault`）。两站继续各自部署，**AdVault 的业务代码、数据和实时同步一概不动**。
- 核对基线（写这份规格时读过的代码，结论已写进下文）：
  - hamark 登录：`web/lib/auth/*`（自建会话 `hamark_session`，库内存令牌哈希，15 天滑动续期；用户按 `wecom_corp_id + wecom_user_id` 唯一；`safeReturnTo` 只放行站内相对路径）。
  - hamark 页签：`web/components/v04/V04LibraryClient.tsx`（四个 `button` 页签，各库一个 `*_ENABLED` 开关，`app/page.tsx` 传入）。
  - AdVault 登录：`src/lib/auth.ts`（next-auth JWT，两个 Credentials provider：账号密码、`wecom`），`src/lib/wecom.ts`（`upsertWecomUserByCode`：**只放行已开通的账号**，先按 `wecom_userid` 再按 `email` 找人，找不到报「账号未开通，请联系管理员开通后再登录」），`middleware.ts`（未登录页面重定向 `/login?callbackUrl=`，API 返回 401），`src/lib/callback-url.ts`（回跳路径规范化）。
  - AdVault 用户表：`users.id BIGINT`，`email UNIQUE NOT NULL`，`password NOT NULL`，`role admin|user`，`status active|disabled`，`wecom_userid UNIQUE`。

## 二、已定的口径（2026-11-03 项目负责人确认）

1. 两站是**同一个企业微信主体**（同一个 CorpID），所以企微 userid 就是两边对人的唯一依据。
2. 两站**不是同一个 Supabase 项目**；本期不共享任何表，AdVault 的用户、案例、活动仍留在它自己的库。
3. 正式域名：hamark `https://hamark.boga.plus`，AdVault `https://advault.boga.plus`。两者同属 `boga.plus`，浏览器视为同站（same-site），`SameSite=Lax` 的 Cookie 在两站间跳转不受影响。
4. 暂无长期合并打算。

## 三、补充产品口径（2026-11-03 项目负责人确认）

1. **「作品库」页签点下去是什么。**（2026-11-03 已定）
   「作品库」直接排在「客户需求复盘库」右边，和前四个页签同一行、同一样式。**点击即在新标签页打开 AdVault**，hamark 留在原处；hamark 里不做作品库的页头、介绍或「进入」按钮，这个页签也不会出现选中态。
2. **没开通 AdVault 账号的人怎么办。**
   定：**保持 AdVault 现在的规则**——只放行管理员已开通（或企微通讯录同步进来）的账号，没开通的人看到「账号未开通，请联系管理员」。
3. **AdVault 自己的登录页。**
   定：没登录时**自动走 hamark**，不再先看到二维码；登录页保留「企业微信扫码」和「管理员登录」两个小入口兜底，给不在 hamark 企微应用可见范围里的人、或 hamark 出故障时用。
4. **退出登录。** 两站会话各管各的：在 hamark 退出不会让 AdVault 退出，反之亦然。本期接受；要做联动退出需另加一套回调，收益小。

## 四、登录流程

所有流程都**从 AdVault 发起**（为了防登录 CSRF，见 5.3），hamark 只负责“我认识这个人”。

```
用户点 hamark 顶栏「作品库」         用户直接打开 advault 的任意链接
            │                                     │ middleware：未登录 → /login
            │                                     │ /login：自动跳转（3.3）
            ▼                                     ▼
  GET advault /api/auth/hamark/start?callbackUrl=/campaigns/12
     ├ 生成 nonce，写 HttpOnly Cookie advault_sso_nonce（10 分钟）
     └ 302 → hamark /api/sso/advault?nonce=…&return_to=/campaigns/12
                 ├ 未登录 → /login?return_to=<本地址>，扫码后回到这里
                 ├ 已登录 → 签一张 60 秒票据（第五节）
                 └ 302 → advault /sso/hamark#ticket=…
                             ├ 前端读 fragment，立刻 replaceState 清掉
                             ├ signIn("hamark", { ticket, callbackUrl })
                             │    └ 服务端校验票据 + nonce + 一次性 + 找人
                             └ 成功 → callbackUrl；失败 → 本页显示原因与兜底入口
```

已在 hamark 登录的人，整条链路是几次 302，**不需要任何操作**。

票据放在 URL **fragment**（`#ticket=`）里：fragment 不随请求发往服务器，不进 Vercel 访问日志，也不进 Referer。

## 五、票据

### 5.1 格式

`base64url(payload JSON) + "." + base64url(HMAC-SHA256(payload 段, 共享密钥))`

payload：

| 字段 | 含义 |
|---|---|
| `v` | 固定 `1` |
| `iss` | `https://hamark.boga.plus` |
| `aud` | `https://advault.boga.plus` |
| `corp` | 企微 CorpID |
| `sub` | 企微 userid（hamark `users.wecom_user_id`） |
| `name` / `avatar` / `email` | hamark 当前存的显示名、头像、邮箱（邮箱可空） |
| `nonce` | AdVault 发起时给的 nonce，原样带回 |
| `rt` | 回跳路径（AdVault 站内相对路径，签在票据里，防篡改） |
| `iat` / `exp` | 签发时间 / `iat + 60 秒` |
| `jti` | 随机 UUID，一次性 |

### 5.2 密钥

- 两站各配一个**同值**环境变量：hamark `ADVAULT_SSO_SECRET`，AdVault `HAMARK_SSO_SECRET`，至少 32 字节随机串，只配在 Vercel，不进仓库。
- 换密钥：两边同时改、各自重新部署；换的瞬间在途的票据作废，用户重试即可。

### 5.3 AdVault 侧校验（全部通过才放行，任一失败都不建会话）

1. 签名用常数时间比较；
2. `v = 1`，`iss`、`aud` 与配置一致；
3. `exp` 未过（允许 30 秒时钟偏差），`iat` 不在未来 30 秒以外；
4. `corp` 等于 AdVault 的 `WECOM_CORP_ID`；
5. `nonce` 等于 Cookie `advault_sso_nonce`，校验后立即清除 Cookie（**防登录 CSRF**：别人拿自己的票据诱导你的浏览器登进他的账号）；
6. `jti` 写入新表 `sso_ticket_uses(jti PRIMARY KEY, used_at)`，主键冲突即视为重放，拒绝；顺手删一天前的行；
7. `rt` 再过一遍 `normalizeAuthRedirectPath`，不合法就回 `/`。

### 5.4 hamark 侧

- `GET /api/sso/advault` 只在 `WORKS_LIBRARY_ENABLED=true` 时可用，否则 404。
- 要求有效的 hamark 会话；`nonce` 必须是 16–128 位 base64url 字符，`return_to` 必须是相对路径，否则 400。
- 只会跳到配置里的 `ADVAULT_URL` + 固定路径 `/sso/hamark`，**不接受外部传入的跳转域名**。
- 响应加 `Cache-Control: no-store`、`Referrer-Policy: no-referrer`。

## 六、AdVault 侧找人与更新

1. 先按 `wecom_userid = sub` 找；找不到且票据带了邮箱，再按 `email` 找（与现有 `findExistingUser` 一致）。
2. 找不到 → 拒绝，提示「账号未开通，请联系管理员开通后再登录」，不自动开户（3.2）。
3. `status = disabled` → 拒绝，提示「账号已停用，请联系管理员」。
4. 找到且可用 → **只更新 `name`、`avatar_url`**；按邮箱找到的补写 `wecom_userid`。**不改 `role`、`status`、`department`、`email`**。
5. 会话内容与现有两个 provider 相同（`id`、`name`、`email`、`role`），下游代码无感。

顺带发现（不在本期范围，单列给负责人判断）：现有扫码登录的 `updateUserFromWecom` 每次登录都会用企微状态覆盖 `status`、把 `department` 写成空。也就是说，管理员在 AdVault 里停用的人，只要企微里还在职，下次扫码会被重新启用。统一登录这条路不会这样做。

## 九、验收清单

1. hamark 已登录，点顶栏「作品库」→ 新标签页直接进 AdVault 首页，没有扫码；hamark 原标签页不变。
2. hamark 未登录，打开 `https://advault.boga.plus/campaigns/<id>` → 跳 hamark 扫码 → 落回同一个活动页。
3. 在企业微信内置浏览器里走 1、2，同样免登。
4. AdVault 里被停用的人：被拒，提示停用；停用状态不被改回。
5. AdVault 未开通的人：被拒，提示「账号未开通，请联系管理员开通后再登录」，不自动开户。
6. 同一张票据第二次使用被拒；超过 60 秒的票据被拒；改动 payload 任一字节被拒。
7. 不经 AdVault 发起、直接访问 hamark `/api/sso/advault?nonce=x` 拿到的票据，在另一个浏览器里用不了（nonce Cookie 不匹配）。
8. AdVault 的 `/login?sso=off` 仍能扫码登录；管理员账号密码登录不受影响。
9. AdVault 登录后的角色、活动、投票、实时同步与上线前一致。
10. 两站开关都关时，线上表现与本期前完全一致。
11. hamark `npm test`、`npm run lint`、`npm run build`；AdVault `npm test`、`npm run lint`、`npm run build` 全过。
