# V1.9 二合一工作台重构｜实施规格 V0.1

> 状态：实施基线（2026-08-24 定稿）
> 交互基线：`docs/demos/2026-08-24-二合一工作台交互demo.html`
> 代码基线：main@d299ccb

## 一、为什么重构

V0.4／V1.9 当前把「一个作品一份公共工作稿、多人共写」作为核心设定，为此背了一整套易碎机制：
工作稿修订号乐观锁、409 冲突重放、变更集三方合并、编辑租约与心跳、本机恢复副本。
线上反复出现的「保存不了 / 发布不了」问题绝大多数源自这条链路。

本次重构用**每位编辑者一个版本**替代共享共写：写入永远只落在本人版本上，
从根上消除并发写冲突，从而可以删掉乐观锁、租约、冲突重放与恢复副本。

## 二、冻结的产品规则

以下 10 条已由 demo 逐条验证并定稿，实施不得擅自改动：

1. **二合一页面**：只读成果页的阅读式展示形态（模块 / 桥段 / 镜头分块）＋ 左侧目录导航，
   同一页既能读又能改，不再有独立的编辑页。
2. **全自动保存**：没有任何保存或提交按钮。编辑框失焦或回车即写库，顶栏显示
   「已自动保存至 vX · 时间」。所见即所存。
3. **原位编辑**：点击可编辑内容就地变成输入框。可编辑区＝正文白字（悬停有淡色底提示），
   不可编辑区＝金褐色字段标签与系统维护的桥段／镜头序号。
4. **版本链，每人一个版本**：
   - 每个工作区内，一名用户最多拥有一个版本（数据库唯一约束保证）；
   - 首次编辑他人版本时，自动基于该版本**当时的快照**创建自己的版本；
   - 快照定格：基版后续如何修改，都与已创建的版本无关；
   - 已拥有版本后，在任何版本上触发编辑都自动切回本人版本；
   - 也可在版本菜单里手动选择基于哪个历史版本创建（仅限尚无版本者）。
5. **版本标识**：`v3（基于v1，张三）`；进入页面默认展示**最新修改**的版本，可手动切换查看任意版本。
6. **插入与时间线**：
   - 插入桥段／镜头的按钮跟随每个桥段和镜头（不在列表末尾）；
   - 新镜头开始时间 ＝ 上一镜头结束时间 ＋ 1 秒；
   - 修改任一镜头结束时间后，其后**所有**镜头级联顺延，各镜头时长保持不变；
   - 桥段序号、镜头序号全局自动重排，由系统维护，用户不可编辑。
7. **时间码速录**：可直接输入纯数字，`0102`→`01:02`、`45`→`00:45`、`5`→`00:05`；
   兼容 `01:02` 写法；秒位 > 59 拒绝保存并提示。
8. **对比基版**：查看有基版的版本时提供开关，开启后标出本版相对**创建时基版快照**的
   修改（就地显示基版原文）与新增（镜头／桥段徽标），并给出汇总。
9. **视频窗口**：进入页面顶部大屏 → 向下滚过后自动缩为右下角小窗（可拖动、视口内钳制、
   播放控制条区域不触发拖动、位置记忆）→ 可最小化为固定右下角的主色胶囊（最小化时不可拖动）
   → 滚回顶部自动恢复大屏并取消最小化。
10. **阅读辅助**：左侧目录可折叠以扩大内容区；每个模块的标题栏（含收起／展开按钮）吸顶浮动；
    页面右侧常驻「到顶／到底」胶囊控件，已在顶／底时对应按钮置灰。

### 模块顺序与字段归属（已调整）

- 第一模块｜全片事实与核心判断
- 第二模块｜脚本反写
- 第三模块｜主导感知类型发生路径与整体评价

字段布局变更：
- 「创意思维链 ｜ 故事参照类型」行在「创意主导手法及机制 ｜ 创意辅助手法及机制」行**之上**；
- 「创意成立契约（隐含情理）」通栏；
- 「整体创意评价」「评价理由」从第一模块**移到第三模块末尾**展示；
  注意：**数据归属不变**，二者仍属于 `factsAndCoreJudgement`，只是渲染位置变化。

## 三、数据架构

### 3.1 原则

- **附加式**：新增一张表，不修改、不删除任何既有表与既有约束；
- **不改 payload 契约**：`V04DraftPayloadV1`、词表、契约校验（`assertV04PayloadContract`）全部沿用；
- **首写物化**：读取永远是纯读取，绝不隐式建行；第一次真实写入才在同一事务内建行
  （沿用 `docs/17` 4.1 已确立的原则）。

### 3.2 新表 `analysis_versions`

```sql
CREATE TABLE IF NOT EXISTS analysis_versions (
  id TEXT PRIMARY KEY,
  workspace_id TEXT NOT NULL REFERENCES collaboration_workspaces(id),
  video_id TEXT NOT NULL REFERENCES videos(id),
  version_number INTEGER NOT NULL CHECK (version_number > 0),
  owner_user_id TEXT NOT NULL REFERENCES users(id),
  owner_name_snapshot TEXT NOT NULL,
  base_version_id TEXT REFERENCES analysis_versions(id),
  base_version_number INTEGER,
  base_payload_json JSONB,            -- 创建时固化的基版快照，用于「对比基版」
  base_captured_at TIMESTAMPTZ,
  payload_json JSONB NOT NULL,
  content_hash TEXT NOT NULL,
  revision INTEGER NOT NULL DEFAULT 1 CHECK (revision > 0),
  taxonomy_version TEXT NOT NULL,
  workflow_version TEXT NOT NULL,
  vocabulary_version TEXT NOT NULL,
  payload_schema_version TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (workspace_id, version_number),
  UNIQUE (workspace_id, owner_user_id),          -- 每人一个版本，由数据库兜底
  CHECK ((base_version_id IS NULL) = (base_version_number IS NULL))
);
CREATE INDEX IF NOT EXISTS analysis_versions_workspace_updated_idx
  ON analysis_versions (workspace_id, updated_at DESC);
```

要点：
- `UNIQUE (workspace_id, owner_user_id)` 是「每人一个版本」的唯一权威，应用层不得绕过；
- `base_payload_json` 让「对比基版」成为纯函数，不需要回溯查询，也不受基版后续修改影响；
- `revision` 只用于同一用户多标签页的最后写入守护，**不再用于跨用户冲突判定**。

### 3.3 既有内容如何进入版本链（懒物化）

- 读取时若该工作区尚无任何版本行：返回一个**虚拟 v1**
  （内容 = 当前公共工作稿 payload，owner = `collaboration_workspaces.created_by_user_id`），
  不写库、不改哈希、不产生历史计数；
- 第一次真实写入时，在同一事务内：
  1. 按 `workspace_id` 加锁并重新检查；
  2. 若仍无版本行，用当前公共工作稿 payload 物化真实的 v1（owner 同上）；
  3. 若写入者就是 v1 owner → 把变更应用到 v1；
     否则 → 以 v1 当时 payload 为 `base_payload_json` 创建 v2，并把变更应用到 v2；
  4. 任一步失败整体回滚。
- 两人并发首写：唯一约束保证只有一人建成，另一人重试后落到自己的新版本，本地输入不得清空。

### 3.4 版本创建与写入规则（服务层唯一入口）

```
saveV04VersionChanges(db, actor, { videoId, basedOnVersionId, changes, changeSetId })
```
1. 解析工作区（不存在则按既有 materialize 流程建立）；
2. 懒物化 v1（见 3.3）；
3. 定位 actor 的版本：
   - 已有 → 用它（忽略 `basedOnVersionId`，因为每人一版）；
   - 没有 → 以 `basedOnVersionId` 指向的版本当时 payload 为基版快照创建新版本，
     `version_number` = 该工作区当前最大号 + 1；
4. 应用 `V04Change[]`（沿用 `applyV04ChangeSet`），再 `assertV04PayloadContract`；
5. 写回 payload / content_hash / revision+1 / updated_at；
6. 追加 `collaboration_revision_events` 审计（沿用既有表；新增列 `version_id` 记录落在哪个版本）；
7. 返回 `{ versionId, versionNumber, revision, contentHash, updatedAt, createdVersion }`。

**不再有**：`expectedRevision` 跨用户冲突判定、409 REVISION_CONFLICT、编辑租约、
本机恢复副本、变更集三方合并。幂等仍保留：同一 `changeSetId` 重放返回既有结果。

## 五之四、灰度上线操作步骤（2026-08-24 已实现，待灰度）

### 上线顺序（不可颠倒）

1. **先执行数据库迁移**：`npm run db:migrate`。它是幂等的，只新增 `analysis_versions` 表、
   一个索引，以及 `collaboration_revision_events.version_id` 列，不修改任何既有表结构。
2. **再部署代码**。此时新页面仍处于关闭状态，线上行为与现在完全一致。
3. **最后打开开关**：Vercel 环境变量新增 `V19_STUDIO_UI_ENABLED=true`。

顺序颠倒（先部署代码后迁移）不会造成数据损坏——新接口只有新页面会调用，而开关未开时新页面不渲染——
但仍应按上述顺序执行，与本仓库既有的迁移先行约定一致。

### 回退

把 `V19_STUDIO_UI_ENABLED` 删除或设为非 `true` 即可，无需回滚代码或数据库：
`/videos/[id]` 立刻回到既有只读成果页，`/videos/[id]/practice` 回到既有编辑页，
两者的租约与冲突链路完全未动。已经产生的版本数据保留在 `analysis_versions` 中，
再次打开开关即可继续使用。

### 灰度期间的观察点

- 是否还有人报「保存不了」——新链路下写入只落在本人版本，不应再出现冲突类失败；
- 版本数量是否符合预期（每个作品的版本数 = 实际编辑过的人数）：
  `SELECT video_id, COUNT(*) FROM analysis_versions GROUP BY video_id;`
- 保存失败是否留下痕迹：新链路的失败只改状态不动本地内容，用户可重试；
  服务端审计仍写 `collaboration_revision_events`（含 `version_id`）。

### 本期未做的收尾

第六章的删除清单**推迟到灰度确认之后**执行。新旧两套并存期间，旧的租约、冲突判定、
本机恢复副本代码全部保留且仍在被旧页面使用，因此不能提前删除。

## 七、验收标准

功能：
1. 两名不同用户先后编辑同一作品，自动生成 v1、v2，互不覆盖；v1 后续修改不影响 v2 内容；
2. 同一用户在任意版本上编辑都落到本人版本，不会产生第二个属于他的版本；
3. 断网／服务端报错时，编辑框内容不丢失，恢复后可继续保存；
4. 时间线：修改结束时间后其后镜头全部顺延且时长不变；插入镜头继承时间并重排序号；
5. 时间码 `0102`→`01:02`，`75` 被拒绝；
6. 对比基版正确标出修改（含基版原文）与新增；
7. 视频窗口三态（大屏／可拖小窗／最小化胶囊）行为符合第二章第 9 条；
8. 页面无任何保存或提交按钮。

工程：
- `npm run build` 通过；
- `npm test` 通过（新增覆盖版本链与时间线级联的单元测试）；
- 生产代码 `npx tsc --noEmit` 不新增错误（基线：仅 `tests/` 下 32 个既有错误）；
- 数据库迁移可重复执行（幂等），且不修改既有表结构。
